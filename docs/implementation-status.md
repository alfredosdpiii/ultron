# Ultron implementation status

Ultron is a fork of Pi whose only agent runtime is the native RLM session worker. This file describes what is built. Whether each acceptance row (A01-A56) is proven is decided by the acceptance runner, not by this file: see [a01-a46-acceptance.md](a01-a46-acceptance.md).

## Runtime

- Every agent run goes through the native session worker: the TUI, `-p`/`--mode json`, and `--mode rpc`. `--help`, `--list-models`, and `--export` never run the agent and use Pi's handlers. `--export` renders native session files.
- `--mode rpc` speaks Pi's JSONL protocol (`src/experimental/rpc-native.ts`); Pi's `RpcClient` drives it in tests. The event stream carries Pi's tool lifecycle (`tool_execution_start`, `tool_execution_update`, `tool_execution_end`). Models are full Pi `Model` objects; `get_tree`, `get_entries`, and `get_fork_messages` cover every branch in Pi's entry format (read from the worker's session storage); `get_messages`, `get_session_stats`, and `compact` return Pi's shapes. Extensions in the session worker reach the attached client through `extension_ui_request` lines (select, confirm, input, editor, notify, setStatus, setWidget, setTitle, set_editor_text) and wait for `extension_ui_response` with Pi's timeout and signal handling; with no client serving (`-p`), dialogs get Pi's defaults at once. `ctx.mode` and `ctx.hasUI` follow the client as in Pi: the CLI tells each Session worker it starts which client it is for ("tui", "rpc", "print", "json"); for the TUI and RPC, `hasUI` is true from `session_start` on and UI calls made before the client attaches are queued for it (Pi's defaults if it has not polled within 30 s); in `-p`/`--mode json` runs it is false. The TUI answers select and confirm with its selector and input and editor with Pi's extension input and editor components. `fork` and `clone` (RPC, and the TUI's `/fork` and `/clone`) create a new session holding only the main lane's path from the root to the entry (fork: any user message in the tree; clone: the current position), with the labels of the copied entries, as in Pi; `--fork` (TUI, RPC, and `-p`) copies the whole session, as Pi's does. Before a fork or clone, the source Session's extensions get Pi's `session_before_fork` (`entryId`, `position`) and can cancel it; the fork's extensions start with `session_start` reason "fork" and the source file, and the source worker's extensions see `session_shutdown` reason "fork" with the fork's file when it retires (unless the Session is used again first). The TUI has Pi's `/tree` over the native tree (branch summary prompt, labels, filters), and a double Esc on an empty idle editor opens the tree or the fork selector per Pi's `doubleEscapeAction` setting. Remaining difference: a worker keeps the mode of the client it was started for, so a later client of another kind attaching to a still-running worker sees that mode (and `hasUI` follows whether a client serves the UI). The Ultron-specific `inspect` command exposes the read-only inspector.
- `-e/--extension <path>` loads extension files in the session worker in addition to discovered ones, and `--no-extensions` skips discovery, as in Pi (paths resolve against the client's cwd).
- Pi extensions from the profile run inside the session worker through the legacy adapter. To stop one loading without deleting it, add an exclusion to the `extensions` setting, for example `"extensions": ["-extensions/jev/index.ts"]` in `<agentDir>/settings.json`. The setting takes exact `-path`, glob `!pattern`, and `+path` forms, with paths relative to the agent directory. This is how to retire the Pi Jev extension. Ultron now does its automatic memory natively. Its model pin and tool guard are deliberately not ported.
- Extension slash commands are registered directly (`/name`, as in Pi) and via `/extension <name>`. `/agents`, `/memory`, `/skills`, `/experiments`, `/goals`, and `/progress` read recorded runtime state without starting work or searching.
- Busy session workers survive the client exiting: background jobs, child lanes, and a root turn in flight keep running, the next `ultron` reattaches, and idle workers retire. Leaving the app (Ctrl-C twice within 500 ms or Ctrl-D on an empty editor in the TUI, a signal to the TUI or RPC process, closing RPC stdin) is not an abort; Esc in the TUI (which, as in Pi, first returns queued messages to the editor) and RPC `abort` are. A single Ctrl-C clears the editor. In `-p`/`--mode json` print runs, SIGINT, SIGTERM, and SIGHUP abort the running turn before the process exits, as in Pi. After a hard kill, idle workers exit within about a second and busy ones finish first.
- Several `ultron` processes share the per-user server directory without disturbing each other (`src/experimental/coordinator.ts`, protocol 4). Each process runs its own server generation with its own options and environment; the coordinator keeps every live generation (a new one never replaces an older one or closes its connections), each client connects straight to its own generation's endpoint, and each Session worker is owned by the server that launched it. A server that starts or opens a Session asks the other workers who owns them: orphans (their server exited with work still running, or died) are adopted, and a Session whose worker another live server owns is refused with "open in another Ultron process" rather than taken over. A generation that is not held open (an automatically activated server) retires once it has no clients or workers, and the coordinator exits when nothing is left. A coordinator of another protocol (an older release) is left alone: the new server runs under an ID derived from the logical one until the old sessions end. When the TUI's Session worker stops unexpectedly, the TUI attaches the Session again once, which starts a fresh worker (jobs of the lost worker are gone); a lost server or a second loss is reported as "The Ultron server stopped (…); your session is saved — run `ultron -c` to resume", as are the same errors in `-p`, JSON and RPC runs.
- `ultron migrate import-pi | export-pi | backup | restore` moves whole Pi session trees in and out (every branch, labels, model and thinking-level history, context edits applied per branch, Pi-reported usage imported into the usage ledger as a marked historical root; Pi-only entry types kept as `pi-session:<type>` custom entries) and rehearses profile backup and restore.
- `/rlm` (`app.rlm.toggle`, Ctrl+R by default) shows the run as a live graph (`src/experimental/rlm-graph.ts`): the root turn, its `rlm` cells, and under the cell that started it everything it ran, with box-drawing connectors, status glyphs (spinner, ✓, ✗, ⊘, ◐ incomplete, ○ queued), elapsed time, tokens and cost. Typed agent tasks, `rlm.spawn` children (with the tasks and shell jobs of their own lanes), `rlm.infer` frames (nested frames under the frame that asked), one `rlm.map` as a single fan-out node with a progress bar (`rlm.map 99 frames ▰▰▰▰▰▰▰▰▱▱ 80/99 · 8 running · 3 incomplete`), workflows as one node with their members and joins (`⇐ plan+code (all)`), background shell jobs, and extension and MCP tool calls made from a cell (`mcp exa-agent_exa_agent_create_run`, labelled by the MCP tool the gateway called, with status, elapsed time, and input and result previews). Tools the model calls directly (native extension tools under the opt-out, or Pi's tools under `ULTRON_TOOLS=native`) are nodes under the turn, so the graph never looks idle while work happens outside the REPL. Finished subtrees collapse automatically, finished work from earlier turns folds into one node, and the panel pins the turn row and windows the rest on the newest live node. Budget gauges show admitted tasks, wall time, tokens, turns and cost against their limits, plus the active inference budget (calls, tokens, depth); a kernel strip shows live, busy, pinned and evicted kernels and their tree memory. Hidden, it collapses to a summary on the runtime line under Pi's footer, which it shares with Jev's presence (`◆ rlm ⠋ turn 1m12s · cell 2 14s · map ▰▰▰▰▱ 80/99 · 6 tasks (2 active) · 2 jobs · 3 tool calls · $0.04`). `/rlm focus` or `app.rlm.focus` (Alt+G; Alt+R is reverse history search) opens it full screen (`src/experimental/rlm-focus.ts`): Up/Down or j/k move, Enter shows a node's details (input and result or error previews, lane, workflow, budget, trace id, frame traces fetched on demand, and the Python call that fetches the full result), c or space collapses, Esc or q leaves; every key is a keybinding. The data comes from read-only inspection: `agents.status {graph: true}` (the newest 300 tasks with lane, start and end times, tokens, cost, bounded input and result previews, workflow membership and a fetch hint; the plain `agents.status` is unchanged), frame summaries in `rlm.frames` (call kind, map size, shared budget id and limits, caller task, lane), `rlm.pool` (per-kernel and total tree memory from /proc, re-read at most every 3 s, and the cap), a bounded output tail on shell jobs, and `toolCalls` (the newest 40 tool calls with source, label, status, times and previews). `/jev` (Alt+J) is Jev's view (`src/experimental/jev-visualizer.ts`): service health and counts (recalled, skipped, kept, refused, failed), a timeline strip of recent turns (`R✓K✓ R·K· R✓K!`, with a legend), needles for the latest recall probability and retention confidence against their thresholds (from `jev.decisions`), the last turn as a decision pipeline (`ask ─▶ gate 0.83≥0.65 ✓ ─▶ recalled 2 ─▶ answer ─▶ keep 0.91≥0.65 stored`), what Jev knows (memories recalled this session, deduplicated, with scope and how often), and the latest raw decisions. Hidden, Jev is a footer presence whose glyph pulses when it decides and spins while a Jev call runs (`⌁ jev: recalled 3 (0.83)`, `⌁ jev: kept (0.91)`). In the transcript, each turn Jev weighed in on gets a muted note under the user message (what memory was injected and why: probability against the threshold, count, scope, the first memory's first words; `app.jev.notes.toggle`, Alt+M, lists them all) and one after the answer (kept, not kept, or withheld as sensitive). Automatic memory tags its gate and retention decisions with `auto:<runId>` (the `ultron-memory` message's `taskId`) and code skill proposals with `skill:<name>`, so notes match turns exactly; turns without injected memory match by time. Spinners and the pulse redraw only while something animates.
- `/rlm pane` or `app.rlm.pane` (Alt+W; Alt+D is the editor's delete-word-forward) opens the RLM pane, the RLM run as dependency waves in a side pane (`src/experimental/rlm-pane.ts`): on a terminal of 120 columns or more the screen splits (`SplitView` in `@ultron/tui`, an hstack layout node, so the chat keeps its scroll view, the editor's cursor, mouse hit-testing, overlays and differential redraws), with chat, editor and footer on the left and the pane on the right (40% of the width, at least 44 columns); narrower, the key opens the full-screen graph instead. The pane shows one run at a time (←/→ switch; the newest live run by default): the current turn, whose `rlm` cells each make one wave ("Same frontier") of the children, typed agent tasks, background tasks and jobs they started (tool calls as one "N tool calls" node per cell, an `rlm.map` as one node with a progress bar, work a child started in the next wave after it), or one `workflows.run` call, whose waves are the topological levels of `dependsOn` and whose nodes not admitted yet show as pending. Each wave is a row of bordered boxes (fold marker, `>` on the selected node, name, `● Running`/`○ Pending`/`✓ Done`/`✗ Failed`/`⊘ Skipped` with elapsed time, and `Start node` or `← dependencies`), wrapping when it does not fit and joined to the next wave by an arrow; then a Dependencies section (`navigation → verify-evidence`) and Node details cards (prompt, name, definition and model, the latest assistant text, elapsed time, turns and tool calls; the selected card and box have an accent border). The header names the run (`RLM · 01a07520`, the turn's prompt, `1/2`, `Running · Done 0/4 · 3 running · wave 1/2`); the footer shows the connection, the scroll position (`1-40/49`) and the keys from the live bindings (`Tab/n next  Shift-Tab/p prev  Space/Enter fold  d Details  ↑↓ Scroll  ←→ Runs  q/Esc Close`). Focused, the pane takes the keys; Alt+W moves the focus back to the chat with the pane still open, q or Esc closes it. The pane also opens by itself, without the focus (typing stays in the editor), when work it shows starts: a spawned child, typed agent or background task, `workflows.run` node or `rlm.map` fan-out that is running or waiting, or that the running turn started. It auto-opens only on a terminal of 120 columns or more and on the chat screen (never the full-screen graph; a run seen while the terminal was narrower opens once it is wide), at most once per turn or run: closing it keeps it closed for the rest of that turn and for the runs it already showed, and the next turn or run with such work opens it again. It never closes by itself. `rlmPaneAutoOpen` (default `true`, listed in `/settings`) or `ULTRON_RLM_PANE_AUTO=off` turns auto-open off. A terminal resized below 120 columns hides the open pane (keys go to the editor) and shows it again when widened. While a run's children or workflow nodes run or wait, the chat column shows a live wave summary above the editor (`▶ <title> running wave 1/2  0/4 done, 3 running`, then one line per node such as `▶ navigation · category:rlm-child@1 · I read this as … · 21s` or `○ verify-evidence · category:rlm-child@1 · waiting 21s`, at most four with `+N more`), polled every second while it shows; with nothing running it collapses to the footer's one-line summary. Two read-only additions to `agents.status {graph: true}` feed it: per task, the lane's `model`, assistant `turns`, `toolCallCount` and `lastText` (the latest assistant text, at most 160 characters), kept live from the harness's `message_end` and `tool_start` events and settled from the run's own entries when it ends; and `workflows`, the newest 20 `workflows.run` plans (run, parent, start and end, and up to 64 nodes each with definition, dependencies, join, and how finished nodes ended, including skipped ones with a bounded reason). The plain `agents.status` is unchanged.
- Live check of the RLM pane (glm-5.3-flash through cliproxyapi, isolated agent and server directories, 6 model calls): at 200×50 one cell wrote a 12-line `notes.txt` and ran `workflows.run` with three independent `rlm-child@1` nodes and a `summarize` node depending on all three. Alt+W opened the pane mid-run: the three nodes side by side as one frontier with the pending `summarize` below an arrow (`← count-words, first-line, last-line`), then wave 2/2 running, then all four done with each card's answer (`The text has 12 lines.`, `1 turn · 0 tools`, `cliproxyapi/glm-5.3-flash`), while the chat column showed the wave summary above the editor until the turn ended.

- `/review` (`src/ultron/review.ts`, `src/ultron/rlm/review_api.py`, `review_prompts.py`) is an optional code review: the worker's AgentController expands `/review [args]` from any client (TUI, `-p`, RPC) into a prompt that runs one cell, `review_api.run(rlm, args)`, which scopes the diff with git or `gh pr diff`, runs specialist finder frames and one verifier frame per deduplicated finding through `rlm.map` under one token cap, and renders a report of confirmed findings only. See [review.md](review.md).

## Native TUI parity with Pi's interactive mode

The TUI (`src/experimental/client-tui.ts`) is a client of the session worker, not Pi's `interactive-mode.ts`. It reuses Pi's components (editor, autocomplete, footer, selectors, tool, bash and assistant message components) over the replicated lane snapshot. New logic lives beside it: `prompt-history.ts` and `prompt-history-search.ts` (history), `client-tui-footer.ts` (Pi's `FooterComponent` fed from the snapshot), `client-tui-commands.ts` (Pi's commands, `/hotkeys`, the startup header), `client-tui-pi-commands.ts` with `client-tui-settings.ts`, `client-tui-auth.ts` and `client-tui-sessions.ts` (`/settings`, `/login`, `/logout`, `/share`, `/resume`, `/import`, `/trust`, `/scoped-models`, `/debug`) and `rlm-tool-renderer.ts` (the `rlm` cell).

Prompt history is appended to `<agentDir>/prompt-history.jsonl` (`{text, cwd, timestamp}` per line; whitespace-only input and an immediate repeat are skipped; a torn last line is tolerated). On start the newest 500 entries are loaded: this project's first, merged by time with the resumed Session's own user messages (deduplicated), then other projects'. Every prompt, steer, follow-up, `!` command and slash command is recorded. Keybinding choice: Ctrl+R stays the `/rlm` panel toggle. Pi has no history search, so its mapping gives no reason to move `/rlm`. Reverse search is `app.history.search` on Alt+R, which no Pi editor or dialog binding uses. Inside the search, Ctrl+R, Alt+R and Up move to older matches, Down (or Ctrl+S) to newer ones, Enter or Tab uses the match, and Esc keeps the draft.

## Model tools

- The RLM REPL (`rlm`) is the root agent's only built-in tool by default, following Prime Intellect's nano-rlm (`DEFAULT_TOOLS = ("ipython",)`): Pi's `read`, `edit`, `write` and `bash` stay registered but inactive. Shell and edits are pre-imported async Python skills in the kernel: `out = await bash('''cmd''', timeout=None)` returns the combined output as a `str` subclass with `[exit code N]`, `[timed out after Ns]` or `[cancelled]` appended and `.exit_code`, `.ok`, `.output`, `.timed_out`, `.truncated`, `.full_output_path`, `.running`, `.job` attributes (the earlier dict shape still works via `out["exit_code"]`); a command still running after `ULTRON_BASH_YIELD_AFTER` seconds (default 30) continues as a host job and the call returns the output so far with `.running` True (see Asynchronous execution); `yield_after=None` blocks until the command ends; `job = await bash(cmd, yield_after=s)` returns a host-owned `ShellJob` instead; `await read(path)` returns a file's text up to `ULTRON_READ_HANDLE_BYTES` (default 256 KiB) and above it a `ContextHandle` from `rlm.load`, printing one line with its size and digest and how to use it (`h.search`, `h.lines`, `h.chunks`, `rlm.map`); `await edit(path, old_str, new_str)` replaces exactly one occurrence and raises `ValueError("old_str must appear exactly once in <path> (found N)")` or `FileNotFoundError`; files are created with ordinary Python. Tools registered by Pi extensions are Python skills in the REPL, not model tools (see Extension tools in the REPL), and child task lanes get the same set as the root (the harness seed). `ULTRON_TOOLS=native` restores Pi's four tools and the extension tools next to `rlm` (the parity and nudge test suites run this way); Pi's `--tools`/`--exclude-tools` still apply when given.
- The system prompt is built by Pi's `buildSystemPrompt` from `src/ultron/rlm/prompt.ts`: the `rlm` tool line and guidelines change with the active tools (REPL-only rules, or "use rlm for data-heavy work" next to native tools), and a `<runtime>` section carries the runtime guide (persistent kernel, `_`, output limits, kernel loss and restore), the skills (`bash`, `edit`, and the rule that project code runs through `bash` with the project's own interpreter because the kernel's Python is not the project's), "Search before delegating" (narrow a corpus with code, print one line per candidate, read the deciding passages, use `rlm.map` only for what stays unclear, never spawn subagents to read documents; the worked example is in `help(rlm)`), bounded inference, delegation (`rlm.spawn`/`collect`, when to delegate, how to brief a child) and one line each for `ctx`, code skills, agents as classes and memory. The guide is kept short because every root and child request re-sends it: 5.1k characters (from 14k, then 9.5k), with one line per API plus the rules, and the `rlm` tool description only names the pre-imported APIs (439 characters, from 2.2k), so nothing is said twice. Examples and API detail (handles, contracts, `Incomplete`, `rlm.map`, `rlm.spawn`/`collect`, `ctx`, code skills, agent classes, typed agents, workflows, background and shell jobs) live in docstrings reached with `help(obj)`. In the default REPL-only mode the base prompt also leaves out Pi's documentation pointers and its "other custom tools" note (`includeHarnessDocs: false`), which describe docs and tools the model does not have; `ULTRON_TOOLS=native` or `--tools` with Pi's file tools keeps them. The first request is 6.6 KB against stock Pi's 5.8 KB (1.15x) in an isolated home (docs/performance.md). The prompt is byte-stable across turns. Skills files are read through `rlm` when it is the only file-capable tool.
- Output handling (nano-rlm's 20 KB `TOOL_OUTPUT_MAX_BYTES`): each captured stdout/stderr stream and the whole `rlm` result are middle-truncated at `ULTRON_RLM_OUTPUT_BYTES` (default 20 000, clamped to 1 KB..128 KiB) with a marker saying how many bytes were cut. A cell's last expression is bound to `_` and, when large (a `str` over 2 000 chars, a container over 40 items, a pandas DataFrame/Series or numpy array), rendered by reference: type, size, head, tail and a sha256 prefix, with a hint to slice it or call `preview(_)`; the object stays in the kernel. A `None` last expression shows nothing, and a failed cell's error shows what it printed before the traceback.
- Images: `await view_image(path_or_bytes, *, detail=None)` (pre-imported, `src/ultron/rlm/view-image.ts` on the host) shows the model an image the way Pi's `read` tool did. It takes a path (png, jpeg, gif or webp, detected from magic bytes, not the extension), raw bytes, a PIL image or a matplotlib figure (`savefig` to PNG in a `BytesIO`); bytes and rendered images go to a temporary file the kernel deletes after the call. The kernel sends an `rlm.view_image` host request naming the file; the host reads it through Pi's pipeline (`detectSupportedImageMimeType`, `processImage`: conversion and auto-resize to the model's `inputLimits.images.resize`, honoring `images.autoResize`; `detail="low"` caps the long side at 512 px) and keeps it with the running cell (a per-cell host handler on `RlmKernel.execute`, so queued cells never mix images). It returns a one-line description (`image 1: 800x600 PNG, 41.2 KB`, plus `downscaled from WxH` when resized); at most 8 per cell (the ninth raises). The `rlm` result is then `[{type: "text"}, {type: "image", data, mimeType}, ...]`, Pi's read-tool shape: the image never appears as printed base64, so the 20 KB truncation cannot touch it. - `scripts/eval-quality.mjs` counts tool calls by name (`toolsByName`) per run and prints them on the per-run line, so a run that never used `rlm` is visible.

## Extension tools in the REPL

Prime Intellect's RLM harness exposes MCP tools as pre-imported IPython skills; Ultron does the same for every tool a Pi extension registers, so a model cannot route real work around the REPL (as it did through pi-mcp-adapter's `mcp` tool, running six Exa research runs with one `date; ls` cell in the graph).

- `src/ultron/rlm/tools_api.py` (kernel) and `src/ultron/rlm/extension-tools.ts` (the `tools.*` host module in the session worker). `await tools.list()` gives names and first-paragraph descriptions, `await tools.describe(name)` the full description and JSON-schema parameters, and `r = await tools.call(name, {...}, **kwargs)` or `await tools.<name>(**kwargs)` runs the tool (`-` and `_` in names match). The worker runs the real extension tool as the harness would: `prepareArguments`, schema validation and coercion (`validateToolArguments`), the extension context with the UI bridge, and the cell's abort signal. The result is a `ToolResult` (a `str` of the text parts joined, with `.details`, `.id`, `.ok`, `.truncated`, `.elapsed_seconds` and `.json()`, which also reads the adapter's `text + "structuredContent:" + JSON` shape); the text is middle-truncated by `truncateToolOutput` at `ULTRON_TOOL_RESULT_BYTES` (default 256 KiB, 1 KiB..512 KiB: the value is data, and printing it is still cut to the 20 KB cell budget) and `.details` is capped at 64 KiB of JSON. A throwing tool raises `ToolError` (`.name`, `.status`, `.details`); validation errors and unknown names (with the available list) raise too.
- MCP is native (`src/extensions/mcp`, `packages/mcp`; see `packages/coding-agent/docs/mcp.md`): a built-in extension of the session worker connects the servers of `mcp.json` on first use and registers one `mcp` gateway tool, which lives in the REPL like every extension tool. pi-mcp-adapter is no longer needed and is left out when installed.
- `mcp` is a thin namespace over that gateway tool, whose modes are selected by parameter (action > tool > connect > describe > instructions > search > server > status): `await mcp.servers()` (`{}` → `details.servers`), `await mcp.tools(server=None)` (`{server}` → `details.tools`, connecting a lazy server on `not_connected`; all servers without an argument), `await mcp.describe(tool, server=None)` (`{describe}` → name, server, description, `inputSchema`), `await mcp.search(query)`, `mcp.connect(server)`, `mcp.instructions(server)`, and `await mcp.call(tool, args=None, *, server=None, **kwargs)`, which sends `{tool, args: {**args, **kwargs}, server?}` (a JSON string for `args` is parsed first). `await mcp.exa_agent.exa_agent_create_run(query=...)` resolves the attribute to a configured server name (non-identifier characters as `_`) and sends the tool's upstream name with `server`. A gateway result whose `details.error` is set (tool not found, server not connected, auth required, a tool error) raises `McpError`.
- Async: like a plain `bash`, a call still running after `ULTRON_TOOL_YIELD_AFTER` seconds (else `ULTRON_BASH_YIELD_AFTER`, default 30; `0`/`off` blocks) keeps running in the worker and returns a `ToolResult` with `.running` True and `.call` its `ToolCall`; `yield_after=s` returns a `ToolCall` after at most `s` seconds (`.result(wait=None)`, `.cancel()`, `.refresh()`), `yield_after=None` blocks. A call outlives its cell and kernel restarts (`tools.get(id)`, `tools.result(id)`, `tools.calls()`); a cell stopped while waiting cancels it (unless it asked for a handle), Esc on the root turn cancels the calls it started, and at most 32 run at once. When a detached call ends while no cell waits on it, a `<runtime_event kind="tool_done" ... fetch="await tools.result(&quot;call-…&quot;)">` is delivered like a job's (re-invoking an idle root); `async.pending` counts running calls for `-p`.
- Every call is journaled as the session value `ultron.module/tool-calls` (the newest 64, previews only; a call running when the worker died reads as interrupted) and listed in `agents.status` as `toolCalls`. The worker also records every non-`rlm` tool the model calls directly (harness `tool_start`/`tool_update`/`tool_end`; a run that ends without a result marks them cancelled), as `source: "native"`.
- Model tools: by default the model's tool list is `[rlm]`. `ULTRON_EXTENSION_TOOLS=native` (or `ULTRON_TOOLS=native`, or `"extensionTools": {"mode": "native"}` in settings.json) restores extension tools as model tools as in Pi; `ULTRON_NATIVE_EXTENSION_TOOLS=a,b` (or `extensionTools.native`) keeps named tools native in REPL mode; `ULTRON_EXTENSION_TOOLS=repl` wins over `ULTRON_TOOLS=native`; `--tools name` names an extension tool explicitly and makes it native. Native tools stay callable from Python. An extension's `pi.setActiveTools` cannot re-add a REPL-only tool.
- The runtime guide (`extensionToolsPrompt` in `prompt.ts`) gets an `## Extension tools` section listing up to 12 REPL-only tools (one line each, then `… N more: await tools.list()`), the MCP servers from the gateway's description, how to call them, the auto-detach rule, and the Exa pattern: start every `exa_agent_create_run` in one cell with `asyncio.gather`, keep the ids, and start the `exa_agent_wait_run` calls with `yield_after=0` so their completions arrive as events. The worker's system prompt is a function re-rendered only when the extension tool list changes, so tools an extension registers later are listed and the cache prefix stays stable otherwise.
- Live check (glm-5.3-flash through cliproxyapi, the real pi-mcp-adapter and Exa MCP server in an isolated profile, 6 model calls and 2 low-effort Exa runs in all): asked to start two Exa runs in parallel, the model called `mcp.tools("exa-agent")` and `asyncio.gather` over two `mcp.call("exa-agent_exa_agent_create_run", ..., effort="low")` from one cell (no `mcp` model tool existed). ## RLM host

- Each lane (the root and every task) has its own persistent Python kernel. Kernels receive no credential-like environment variables and no worker control channel (`ULTRON_RLM_ENV_ALLOW` passes named variables through). A pool caps live kernels (16), evicts idle ones after a snapshot, never evicts a running cell, and pins retained instances' lanes (up to half the pool). Kernels run under per-process memory limits (`ULTRON_RLM_MAX_MEMORY_MB`, default 4096), a whole-tree memory cap over the kernel and every process its cells start (`ULTRON_RLM_MAX_TREE_MEMORY_MB`, default twice the per-process limit, 0 disables), and a per-cell CPU budget (`ULTRON_RLM_MAX_CPU_SECONDS`, default 1800); exceeding any fails the cell clearly and the kernel is replaced if needed. The tree cap uses a transient systemd user scope (`systemd-run --user --scope -p MemoryMax=… -p MemorySwapMax=0 -p OOMPolicy=continue`) when a probe shows it works without root, else a host watchdog that sums the proportional memory (Pss_Anon+Pss_Shmem+SwapPss from `smaps_rollup`, so copy-on-write pages shared by forked children count once; RssAnon+RssShmem+VmSwap where PSS is unavailable) of the kernel's descendants from /proc every 500 ms, every 250 ms above 40% of the cap and every 100 ms above 70% (`ULTRON_RLM_TREE_MEMORY_BACKEND=auto|cgroup|watchdog|off`). The kernel runs in its own session and makes itself a child subreaper (`PR_SET_CHILD_SUBREAPER`) before any cell runs, so processes that double-fork out of a cell are reparented to the kernel and stay counted. On a limit hit or shutdown the host stops the kernel, SIGKILLs its descendant tree in repeated sweeps (catching orphans it adopts meanwhile), then its process group, the kernel, descendants seen by earlier watchdog scans, and any process left in the cgroup scope. Snapshots are HMAC-signed by the host with a per-profile key. Snapshots are signed with `<agentDir>/rlm-snapshot.key` by default; `ULTRON_RLM_SNAPSHOT_KEY_STORE=auto` (or `keyring`) opts into keeping the key in the OS keyring via `secret-tool` (an existing key file is moved there). The keyring hides the key only from casual reads of the profile, not from model code running as the same user, and a locked or unreachable keyring costs restorable snapshots, so it is off by default; unsigned or tampered snapshots are refused.
- The host knows which lane issued each request, so tasks record their parent, child lanes can only query their own subtree, and cancelling a task stops its whole subtree.
- Strategies: `deterministic`, `predict` (one tool-free model call with bounded repair), and `rlm` (a model lane). All share admission, idempotency, timeouts, usage accounting, and the durable journal. Results are always `verification: "unverified"`; only explicit checks (progress reassessment, goals, release gates) can say more.
- The usage ledger (`ultron.usage`) keeps the 50 most recently active roots (root turns and background jobs) call by call. Older roots with no open reservation whose wall deadline has passed are folded into a bounded per-session history (totals by kind, model spend, unknown-priced calls, task admissions by status), so the document stays bounded. `agents.status` shows the current root and a `session` total that includes the folded history; reconciliation compares each root with its own records and the session total with all records plus the history.
- `agents.spawn`, `rlm.spawn`, and module-started tasks outlive the Python cell that started them; `agents.invoke` waits inside the cell. Each root turn gets its own wall budget (`ULTRON_MAX_WALL_MS`, default 30 minutes) and admission cap (`ULTRON_MAX_ADMITTED_TASKS`, default 24); a child's deadline is capped at its root's remaining budget. An optional cost cap (`ULTRON_MAX_COST_USD`, unset by default) refuses new model-backed work once reached or when pricing is unknown. Optional per-root turn and token limits mirror nano-rlm's `max_total_turns` / `max_total_tokens` (settings `rootBudget: {maxTotalTurns, maxTotalTokens}`, overridden by `ULTRON_MAX_TOTAL_TURNS` / `ULTRON_MAX_TOTAL_TOKENS`; `off` removes a limit; unset by default). The usage ledger counts every model response of a root turn and of every lane it admitted (`rlm.spawn` children and their descendants, `rlm.infer`/`rlm.map` frames, typed agents, background jobs; each `predict` attempt too) with its provider-reported tokens and cost, charged to the admitting root through `usageRootForLane`. The turn, token and cost limits all read that per-tree tally, so a runaway sub-agent tree is stopped by any of them: once a root's tree reaches a limit, `before_request` refuses the next model request on every lane of the tree (children and the root itself), new model-backed work is refused at admission, tool calls are blocked with the limit error, and a task whose run was stopped fails with the limit message (`Usage token limit reached for root turn:…: 40210 of 40000 tokens used (max_total_tokens …)`, `Usage cost cap reached for root turn:…: spent $0.0203 of $0.02 (ULTRON_MAX_COST_USD)`). Each response is counted once: a frame's or child's settled model call describes the same responses and is not added again, and a frame's own `Budget` is a nested cap inside the root's totals (its spend counts toward both). Each root turn starts fresh; `agents.status` shows the tree's `spend` (`turns`, `tokens`, `costUsd` and the three limits). The tally is kept in memory without a limit and written through per response only while a turn, token or cost limit is set.
- `agents.spawn`, `rlm.spawn`, and module-started tasks outlive the Python cell that started them; `agents.invoke` waits inside the cell. Each root turn gets its own wall budget (`ULTRON_MAX_WALL_MS`, default 30 minutes) and admission cap (`ULTRON_MAX_ADMITTED_TASKS`, default 24); a child's deadline is capped at its root's remaining budget. An optional cost cap (`ULTRON_MAX_COST_USD`, unset by default) refuses new model-backed work once reached or when pricing is unknown. `rlm.spawn` subagents nest at most `ULTRON_SPAWN_DEPTH` levels (a ceiling, default 3; 0 removes it). Below it, nesting is opt-in per spawn: a subagent may spawn only if its parent passed `rlm.spawn(..., depth=N)` (default 0), and passes down less than it was given; a deeper spawn raises an error that tells the model to do its part itself. On the research task each level of re-splitting multiplied the prompt and transcript cost (docs/performance.md).
- Bounded inference (`src/ultron/rlm/inference.ts`, `infer_api.py`): `h = await rlm.load(path | text | bytes)` interns the content in the kernel and stores it content-addressed (`<session dir>/rlm-context/<session id>/<sha256>`); the handle prints only `label`, `size`, `digest`, and `h.slice`, `h.lines`, `h.search`, `h.count`, `h.chunks` produce views (only a printed view puts text into the model's context); `await rlm.open(digest)` reopens a stored handle. `await rlm.infer(task, context=[views, literals, handles], contract=schema | int | str | ..., budget=Budget(calls, tokens, depth), max_repairs=2)` runs an *inference frame*: an `rlm-frame@1` task admitted like `agents.invoke` (journal, admission and wall budget, usage ledger, cancellation cascade; the calling cell's abort cancels it), on its own lane with a frame system prompt, no parent transcript, and no tools (depth > 1 adds only the `rlm` cell, where whole handles arrive by reference and nested frames draw on the frame's budget with one level less depth). A reply that fails the JSON-schema contract is re-asked on the same private conversation within budget; running out returns an `Incomplete` (falsy; status `contract_unmet` / `budget_exhausted` / `depth_exhausted`, spent and remaining budget, trace id, the last three bounded outputs). `await rlm.map(task, items, ...)` fans frames out under one shared budget in order (concurrency 8), with per-item `Incomplete` / `FrameError` entries. A top-level map without a token limit gets a default one (`ULTRON_RLM_MAP_TOKENS`, 500,000), so a map over a whole corpus stops with `Incomplete` entries whose detail says how to raise it instead of spending millions; the result is a list (`MapResults`) with `.spent`, `.budget` and `.remaining`, and the map prints one line (`[rlm.map] 40 frames: 38 complete, 2 incomplete, 0 failed; spent 40 calls, 81,200 tokens of 500,000`) so the model sees what it spent. Without `max_repairs`, a scalar contract (int, float, bool, str, null) is re-asked once and any other contract twice. A frame's message has no per-frame totals before its views, so a map's frames share the task and the shared `context=` views as one byte-identical, cacheable prefix. Every provider request of a frame holds one call plus an input estimate and an output tranche (at most a quarter of the remaining token pool and 16k; it also caps the request's max output tokens), settles against the reported usage (cache reads charged at a tenth), and releases the hold, so a failed request refunds its tranche; holds and charges apply along the whole budget tree, so siblings cannot oversubscribe a shared pool. The first call of each frame is claimed at admission, in order. Model calls are recorded in the usage ledger with their `budgetId`. Frame traces (task, view metadata, contract, budget, attempts, per-request tranches and charges) are session values `ultron.rlm.frames/<id>` with an index at `ultron.rlm.frames/index`; `await rlm.frames()` and the `/rlm` graph read them.
- Workflows validate before any effect and support fan-in, conditional routes, any-of joins (`join: "any"`), bounded revision loops (`revise: {from, until, max_rounds <= 10}`, each round its own task), explicit skips and failures, and keyed nodes and workflows.
- Subagent verdicts (`src/ultron/rlm/verdict.ts`, `src/ultron/workspace-snapshot.ts`): an `rlm.spawn` child ends with `await rlm.finish(status, summary, evidence=[...], outputs={...}, changed_files=[...])` and a short reply. The host checks the call mechanically: `status` is `passed`, `failed` or `blocked`, the summary is nonempty, fields have the right types and bounded sizes, and `passed` needs evidence of which at least one item is concrete (a command with its exit status or counts, a file path, a `:line`); no model judges it. A rejected call raises in the child's cell with every problem, and the child may fix it twice; a third rejection with no valid verdict recorded leaves the child unverified with `check.outcome: "invalid"` and the problems. The host snapshots the session's working directory when the child's lane starts its run and again when it ends, and compares the declared `changed_files` with what changed. A snapshot records metadata only (size, mtime and ctime in ns, mode, inode; link targets): inside Git, the files of `git ls-files --cached --others --exclude-standard` (ignored files never count), elsewhere a walk that skips dependency and cache directories and does not follow links; both bounded at 200,000 entries (4,000 files take tens of milliseconds). Attribution under concurrency: children share the filesystem, and siblings, the parent's cells and background jobs may write while a child runs, so a change seen during its run is not proof that it made it. The check is therefore asymmetric. A declared file that did not change during the run (or does not exist and was never listed) is a false claim whoever else ran, and makes the verdict `contradicted` (`unobserved`). A file that changed but was not declared is listed in `unreported` and never fails the verdict; paths that the verdict of another overlapping task already declared are left out, and `concurrent` names the overlapping tasks (outside the child's own ancestors and subtree; frames excluded) so the parent can attribute the rest. A declared file the snapshot does not list (ignored, or outside the directory) is `unlisted`, not checked. `rlm.collect`, `agents.result` and the journal carry `verdict` (null without one), `check` (`outcome`: `verified`, `contradicted`, `invalid` or `unchecked`, with `unobserved`, `unreported`, `unlisted`, `concurrent`, `reason`), and `unverified: true` for a child that ended without a valid verdict; its reply is still its `value`, and without a workspace to observe it gets no `check`. An empty final reply after a verdict falls back to the summary. `child_done` summaries lead with a tag (`[passed, verified]`, `[passed, contradicted; declared but unchanged: a.ts]`, `[unverified]`). The guide tells subagents to finish this way and the root to trust only verdicts whose `check.outcome` is `verified`. In `workflows.run`, an `rlm-child` node whose verdict is `failed` or `blocked`, or `contradicted`, fails the node (so `join: "all"` dependents are skipped); a later node's `inputFrom`, `when` and `revise.until` bind the checked verdict (`status`, `summary`, `outputs`, `evidence`, `changed_files`, `check`, `reply`) instead of the reply text, and a revision reviewer's verdict is data for `until`, not a failure. Workflows have no declared required outputs, so none are enforced. The verdict fields are optional additions to the version-1 task journal; an older build refuses a journal that has them as invalid rather than overwriting it. The snapshot module (`snapshotWorkspace(cwd, options)`, `diffSnapshots(before, after)`) is independent of subagents so per-cell checks can reuse it.
- Host modules (`src/ultron/*.ts`, Python classes in `src/ultron/rlm/*_api.py`):
  - `schedules` / `goals`: slot-keyed schedules that never double-fire, missed ticks coalesce, goals achieved only by passing required checks.
  - `skills`: version-pinned (content hash), explainable selection; frontmatter cannot grant capabilities.
- Code skills (procedural memory as tested code, `src/ultron/code-skills.ts`, rows A53-A54). `await skills.propose_code(name, source, test_source, evidence)` writes a new numbered version to `<agentDir>/skills/<name>/.versions/<n>/` (`skill.py`, `test_skill.py`, generated `SKILL.md`; `ULTRON_CODE_SKILLS_DIR` overrides the directory) and runs its `test_*` functions (sync or async) in a fresh kernel in a temporary directory, on a copy of the files, with every host request refused and a wall budget (`ULTRON_CODE_SKILL_TEST_TIMEOUT_MS`, default 120 s). Only a passing version becomes active; a failing, empty, or unimportable one is kept as `rejected` for inspection. Versioning follows refinements: an activation supersedes the previous active version and remembers it, `await skills.rollback(name, version)` accepts only the active version and restores the one it superseded (or leaves none active), and the per-skill `.history.json` records every state change, the test report, the evidence, and Jev's score. Proposals and rollbacks are also journaled in the session's skills module document. The active version is copied to the skill directory's top level, so Pi's skill catalog lists its `SKILL.md`, and is importable in every kernel as `from code_skills import <name>` (also `import code_skills.<name>`); the package is named `code_skills` so it never shadows the `skills` API object. Imports resolve to the active version at import time (a rollback takes effect in running kernels on the next `from code_skills import`), and only a file whose sha256 matches the tested source loads. The rlm tool description lists active skills (docstring summary and signatures, at most 24 entries and 3000 characters), read on every model request. `skills.code_list(kind=, family=)` and `skills.code_history(name)` inspect them. `skills.propose_policy(name, plan, test_source, evidence, family=)` stores a decomposition plan (a module defining `plan(...)`, or a plan function with retrievable source) as a policy skill the same way; its test must also find a callable `plan`. Phase 2 is expected to record successful `rlm.map` plans through it.
- Jev judges each code proposal (`skillPolicy`, recorded as a `retain` decision): `keep`/`skip` is recorded as relevance and never blocks a deliberate proposal; `sensitive` refuses it before anything is written. Secrets in the source, test, or evidence are refused deterministically even without Jev. A Jev outage is recorded and never blocks.
- After 8 consecutive tool rounds whose calls all succeeded, the root agent is steered once per run with a one-line suggestion to save the procedure as a code skill (`ULTRON_SKILL_NUDGE`, 0 or `off` disables).
  - `agent_message`: parent/child messaging with verified senders, deduplication, expiry, inbox caps, optional steering, and verifier isolation.
  - `progress`: evidence receipts, progressing/busy/stalled/finished assessment, completion claims verified only by a passing verifier; budgets never extend.
  - `instances`: retain a completed task and continue it on its own lane with fresh scratch and a persistent `state` dict.
  - `grants`: scope/revision/policy/owner/expiry-bound approvals, rechecked on use; dormant by default.
  - `gates`: frozen release-gate definitions and baseline/candidate comparison where required regressions block.
- Agents as Python classes (`src/ultron/rlm/agent_class_api.py`, A55): `@agent` on a class, or subclassing `Agent`, makes it an agent in any kernel. The class docstring is the role; an `async def` method whose body is only a docstring and `...` becomes an `rlm` definition `<class>--<method>` registered through `agents.register`, and each call is one typed `agents.invoke` whose instructions are the class and method docstrings and whose input is `{args, state}` data (arguments and public fields; a value over 16 KB, `max_arg_bytes`, is replaced by a bounded `preview` plus a 0600 JSON file holding the full value, under `ULTRON_RLM_SPILL_DIR` or a per-user temp dir). Input and output schemas come from annotations: str, int, float, bool, None, Any, list/Sequence, dict[str, T], tuple (fixed and variadic), set/frozenset, Optional/Union, Literal, Enum, Annotated (string metadata becomes a description), dataclasses, TypedDict (Required/NotRequired), and pydantic models (references inlined, keywords the registry refuses dropped); anything else fails at class definition with the reason. Arguments are checked in the kernel before admission; returns are checked by the host, and for class-derived definitions (marked `x-ultron-agent-class` in their schemas) the host's error names the failing path, e.g. `$.kind must be equal to one of the allowed values ("bug", "feature")`. A bad return raises `AgentCallError` (with the host result) and stays a failed, unverified task. Methods with real bodies run in the kernel. Annotated fields are durable state stored as JSON in `state["__agents__"]`, keyed by class and instance key (`Triage("main")`); assignments are type-checked, in-place mutations are written back after each cell and before a snapshot, and fields starting with `_` are kept but not shown to the model. The class source (with the imports and top-level definitions it uses from its cell) is stored there too, so after a snapshot restore or a scratch reset the class is defined again and instances reattach by key. Every distinct set of method descriptors is a generation (the definition version): an identical redefinition reuses its generation, a changed one registers the next, `Cls.at(n)` calls generation n with its own source and contracts, and `await Cls.rollback(n)` makes it current. `agent.schema(T)` exposes the schema derivation. Options: `@agent(name=..., model="provider/model", timeout_ms=..., max_arg_bytes=...)`.
- Model-owned context (`src/ultron/context-control.ts`, kernel `ctx` from `rlm/context_api.py`): `ctx.history(limit, kinds)` lists the items in the lane's context (after the newest compaction, oldest first) with ids, kinds, current and original byte sizes, a one-line preview, state (`visible`, `forgotten`, `summarized`, `collapsed`, `replaced`), and pinned/protected flags; `ctx.get(id)` returns one item in full with what the model sees of it; `ctx.forget(ids, reason)` and `ctx.summarize(ids, text)` append a context edit; `ctx.pin(id)`/`ctx.unpin(id)` and `ctx.note(text)` append their own entries. A context edit is a `context_edit` custom entry on the branch (Pi's `context_edit` in native form: `{ edits: [{ targetId, replacement }] }`, null omits, `{ content }` replaces), applied by the harness when it builds model context (`applyContextEdits` in `@ultron/agent-core`) and before compaction summarizes. The transcript keeps every entry, and like refinements an edit only applies on the branch that carries it. Tool calls and results stay paired: omitting an assistant message (or a replacement that drops its calls) omits their results, an omitted result whose call stays visible becomes a stub, and a summarized span always includes whole call/result pairs. Guard rails: the current user message, a call still waiting for its result, and pinned items are never edited; a request with any refused id changes nothing. Edits made while a turn runs land at the next turn boundary, and later `ctx` reads in the same cell already see them. Every edit that lands on a branch is published to extensions on `pi.events` channel `ultron:context_edit` (`{ lane, editId, source, reason, edits: [{ targetId, action }], tasks? }`).
- Collapse on return: a root-level task (including an `agents.invoke`, `rlm.collect`, or workflow node) that ends while a root `rlm` cell runs, or before the next one starts, is attributed to that cell. Once the model has answered after the cell's output, the host appends a `collapse` context edit that replaces the output (when longer than 600 bytes) with a 200-character head and one line per task: definition, key (unless random), status, cost, and `await agents.result("<id>")`. The full value stays in the journal and in any kernel variable; `ctx.get(<entry id>)` shows the original output. Pinned outputs are never collapsed.
- Compaction respects the model's context choices: forgotten items are not summarized back in, and notes and pinned items that a compaction cut off are shown again right after the compaction summary (bounded to 16 KB). The `/rlm` graph panel shows a context line (forgotten, collapsed, pinned, notes) and the latest forgotten and pinned items, from the read-only `ctx.state` inspection request. The prompt fragment for the kernel API is `CONTEXT_PROMPT`.
- Refinements (versioned lessons) reach later task prompts, follow the conversation branch (a lesson from an abandoned branch never applies), refuse protected targets and capability requests, and are content-validated. Approval is off by default and recorded as `not_required`.
- Memory uses Hindsight at `http://localhost:8888` by default (bank `ultron`, created on first use; `ULTRON_HINDSIGHT_URL` overrides, `off` disables). Automatic memory is gated by Jev; deliberate `memory.prepare`/`memory.propose` calls from agent code skip the relevance gate, and writes Jev rates sensitive are still refused. Memory withholds forgotten and superseded items even when the backend still returns them, labels evidence classes, records scope denials, and reuses recorded decisions.
- Automatic per-turn memory (`src/ultron/auto-memory.ts`) runs on root-lane runs only, never on child task lanes, and needs both Hindsight and Jev. Before a run, the user's request goes through Jev's recall gate (the non-explicit path: a low score makes no Hindsight call). Recalled evidence is injected as an untrusted `ultron-memory` custom message. That message stays in the transcript, the TUI folds it into a Jev note under the user message, and `memory.why("auto:<runId>")` explains it. After a completed run, Jev's retention policy judges the request and the answer. Only a keep with confidence of at least 0.65 is stored, as `[User] … [Assistant] …`. Aborted or failed runs are never stored. Scope is `project` by default (`ULTRON_AUTO_MEMORY_SCOPE=session|project|global`). `ULTRON_AUTO_MEMORY=on|recall|off` (default `on`) controls it. Recall and retain decisions appear in `jev.decisions` and the `/jev` panel. A Jev or Hindsight failure is swallowed, so the turn runs without memory. Jev reads `TYPESAFE_API_KEY` or, like the Pi extension, `<agentDir>/jev-api-key`. When the gate retrieves, the Pi Jev extension's Hindsight bank (`ULTRON_HINDSIGHT_LEGACY_BANK`, default `omp`; `off` disables) is also searched read-only, without tags. Up to 12 deduplicated results are appended under "Earlier memory (from Pi, read-only)". A missing bank counts as empty, and Ultron never writes to it.
- Ultron does not route or pin models from Jev triage. The model is the one from `--model`, `/model`, or settings. Triage is available to agent code as `jev.triage`.

- Versioned session values (unreal-agent invariant, `src/ultron/format-version.ts`): every document Ultron writes to the session carries a format version (`ultron.tasks`, `ultron.definitions`, `ultron.usage`, `ultron.memory.state`, `ultron.jev.decisions`, the `ultron.module/*` documents of family, progress, schedules, instances, grants, release-gates and skills, and the `ultron.local` refinements, experiments, artifacts and artifact references). Entries (tasks, calls, memory operations, refinement events, decisions) inherit their document's version, since each document is replaced whole. A document without a version is read as version 1. A newer version fails explicitly, naming the value and version (`Cannot resume: session value ultron.tasks/root has format version 2, but this Ultron reads only format version 1 …`), and is never rewritten: the session worker checks these values before loading any of them (artifacts, which can be large, when read), and each store checks again on load. Transient or foreign values are not versioned: `ultron.session.start/fork` (deleted on first read) and the `ultron.pi.*` import records (Pi's own entry format and a copied-entry id).
- A research-loop brake steers the root agent to answer after 10 consecutive tool-call rounds in one turn, and again more firmly at 20 (`ULTRON_TOOL_ROUNDS_NUDGE`, 0 disables). It never aborts; Esc does.
- Sub-agent worktrees (`rlm.spawn(brief, name=..., worktree=True)`, `ultron/rlm/worktrees.ts`). Before the child is admitted, the spawner's working tree (the root's, or a worktree child's own) is pictured as a snapshot commit: a copy of its index gets `git add -A` and `write-tree`/`commit-tree` on top of HEAD, so the parent's index and files are never touched. The child's branch `ultron/<session>/<name>` (never reused: a taken name gets a suffix) starts there, checked out in `<git common dir>/ultron-worktrees/<id>` next to a record naming the owning process. Setup links the gitignored `node_modules` (entry by entry, workspace links pointing into the worktree), `.venv` and `venv` directories (a directory of links, so `dir/` ignore patterns still match) and copies small `.env` files; `worktree_setup=` or the `worktrees` setting replace the lists and add a command run before the child starts (its failure fails the child). The child's lane, and the lanes of its descendants without a worktree of their own, work there: kernel cwd and `ULTRON_WORKTREE`/`ULTRON_PARENT_REPO`/`PWD`, host `bash` and shell jobs, Pi's native file tools (`ULTRON_TOOLS=native`), file hooks and Loki (the guard checks the worktree's root), Claude Code lanes (`ultron --claude`) and `claude -p` children with their `ultron mcp --child` server (`ultron claude`, via `ULTRON_CHILD_CWD`). The brief gets a note saying so. `read`/`edit`/`write`/`view_image`/`rlm.load` map absolute paths into the parent's checkout to the worktree's copy (printed once per path), and `rlm.finish` does the same for `changed_files`. The verdict check pictures the worktree (siblings in other worktrees are no longer "concurrent"), and the parent's tree too: files changed there while the child ran and declared by no other task are listed as `check.outside`. When the child ends (any status), `git status` in its worktree, minus the setup paths and files unchanged since its start picture, is committed on its branch (hooks, signing and trailers off; message from the verdict summary). The result gets `worktree: {task, branch, path, repo, base, commit, changed_files, diffstat}`, and an empty child's worktree and branch are removed at once. `rlm.merge(children, on_conflict="stop"|"skip"|"markers", include_failed=False)` waits for the children, then merges each in order, one merge at a time per host: base = the child's snapshot commit, ours = a fresh snapshot commit of the target tree, theirs = the child's commit, via `git merge-tree --write-tree --merge-base` (Git 2.40 or newer). A clean result is written into the working tree through a temporary index and `checkout-index` (smudge filters and modes apply, the real index is untouched), after checking that no file it writes changed since the snapshot; changes are left uncommitted. A conflict writes nothing and reports files, conflict kinds and hunks (line, ours, theirs), and the merge stops (`skip` goes on; `markers` writes the conflicted result with `working tree`/branch labels). Merged and empty children's worktrees and branches are removed; conflicted and failed ones stay. Host close removes this session's finished, unmerged worktree directories and keeps their branches. At host start, records whose owner process is gone are pruned: uncommitted work is committed on the branch first, branches holding work are kept, and `git worktree prune` runs. `rlm.worktrees.list()`/`cleanup(branches=False)` do this by hand, and `ULTRON_KEEP_WORKTREES=1` keeps everything. `worktree="auto"` falls back to the shared tree without Git, a repository or a commit. Loki never auto-installs or auto-commits `.loki/` in a worktree (path under `ultron-worktrees`, or `ULTRON_WORKTREE` set). `workflows.run` nodes take `worktree: true` (rlm-child nodes only, not with `revise`), and a node branches from the caller's tree when it starts: a dependent node does not see an upstream node's work until it is merged. The RLM pane shows a worktree child's branch and merge status in its details. Limits: submodules are not initialized in worktrees, LFS needs git-lfs, a linked `.venv` with an editable install imports the parent's sources, and children share linked dependencies and ports.

## Asynchronous execution (Unreal Agent's model)

- Host-owned shell jobs (`src/ultron/rlm/shell-jobs.ts`, nano-rlm's `rlm.shell.run` adapted): `job = await bash(cmd, yield_after=s, timeout=None)` starts the command in the session worker (Pi's shell operations, as the blocking `bash` uses, with process-tree kill) and returns a `ShellJob` after at most `s` seconds (0 returns at once; capped at an hour), finished or still running. The handle has `.id`, `.running`, `.status`, `.exit_code`, `.ok`, `.text` (at most 16 KiB: head and tail around a marker naming the omitted range), `.truncated`, `.timed_out`, `.cancelled`, `.output_path`, `.output_bytes`, `.elapsed_seconds`, `.error`, and `await job.result(wait=None)`, `await job.cancel()`, `await job.read(cursor, max_bytes)`. `await rlm.job(id)` recovers a handle after its variable is lost (kernel restart, eviction, scratch reset); `await rlm.jobs()` lists them (a child lane sees only its own). Plain `await bash(cmd)` runs through the same jobs (host request `shell.bash`) with a default wait of `ULTRON_BASH_YIELD_AFTER` seconds (30; `0` or `off` restores the fully blocking bash, as does `yield_after=None` per call). A command that ends in time returns the usual finished `BashOutput` (the whole output, read back from the spill file when it is over the 16 KiB job text) and announces nothing; one still running keeps running as a job and the call returns a `BashOutput` that is still a `str`, with `.running` True, `.job` its `ShellJob`, `.exit_code` None and `.ok` False, the output so far and the line `[still running as job job-… after 30 s; its completion will arrive as a runtime event, or `await <result>.job.result()` to wait]`; its end is announced like any job's. A cell stopped during the wait cancels the command, as the blocking bash did. Nothing in the codebase relied on a finished `bash` beyond the model: code-skill test kernels have no host requests, agent classes do not call `bash`, and kernels whose host handler only knows `bash` (tests) ignore the `yield_after` field and block. A job belongs to the lane and root turn that started it: it outlives the cell, kernel restarts and eviction, and stops on its timeout, `cancel()`, an Esc/RPC abort of its root turn, or worker shutdown (not when a client merely exits; the worker stays busy while jobs run). Output is sanitized like Pi's bash and spilled to `<session dir>/rlm-jobs/<session id>/<job>.log`, keeping the first 4 MiB plus the last 8 KiB in memory; the 64 newest finished jobs and their files are retained. At most 32 jobs run at once. The job list is the versioned session value `ultron.module/jobs`; a job still running when the worker died reads as `interrupted`. `agents.status` lists the 20 newest jobs and the `/rlm` graph shows them under the lane that started them. `asyncio` is pre-imported in every kernel.
- Completion events instead of polling (`src/ultron/async-events.ts`). When a `yield_after` job, an `rlm.spawn` child, an `agents.spawn` task or a background job ends while no cell is waiting on it (a `job.result()`, `rlm.collect`, `agents.result` or `background.result` in progress gets the result inline and suppresses the event), the host appends one `ultron-runtime-event` custom message (Pi's `CustomMessage`, `display: true`, so RPC and TUI clients show it like any custom message) to the lane that owns the work: the root for root-owned work, the parent task's lane for a child's. Each completion is one line, `<runtime_event kind="job_done|child_done|task_done" id="..." status="..." summary="..." fetch="await rlm.job(&quot;...&quot;)" />`, with a 240-character summary (a job's exit status and last output lines; a task's definition and value head or error) and the call that fetches the full result. Completions within 500 ms of the first become one message.
- Delivery. A lane that is running gets the message as a steer: the harness places it at the next turn boundary, or continues a run that was about to finish with it. A steer that a run did not consume (it ended in between) is taken back with `cancelQueued` and delivered again. An idle root lane is re-invoked: the message is accepted as the prompt of a new run, as Unreal calls the model again. A child lane is never re-invoked; its events wait as `nextRun` input. The TUI's Esc returns only user-typed queued messages to the editor, never events.
- Guards. The re-invoking run is charged to the root that started the work (`NativeRlmHost.continueRootTurn`), so the per-root turn and token limits, wall budget and cost cap keep counting across the chain; when any is spent, or after 16 automatic runs in one chain (`ULTRON_ASYNC_EVENTS_MAX_RUNS`), or when the root turn was aborted, the event is delivered quietly as `nextRun` input (seen with the next user prompt) and no run starts. Esc (or RPC `abort`) on a root turn cancels the shell jobs it started and their ends are not announced; completions of tasks from an aborted turn never restart the model. `ULTRON_ASYNC_EVENTS=off` disables events (jobs still work and are waited on with `result()`), and the runtime guide then tells the model to wait explicitly.
- `-p` and `--mode json` follow event-triggered runs: after the prompted turn the client asks the worker (`async.pending` inspection) whether root-owned work that can still re-invoke the model is outstanding, waits for the runs its events start, and prints the last run's answer.
- The runtime guide (Runtime, Skills, Delegation) explains auto-detach, `yield_after`, handles and `<runtime_event>` messages: start long work, continue or end the turn, never sleep or poll, and batch independent operations in one cell with `asyncio.gather`.
- Prompt-cache safety. Events are only ever appended (a steer at a boundary, a new run's prompt, or `nextRun` input before the next prompt); nothing is inserted before earlier messages. `test/ultron-async-cli.test.ts` captures successive request bodies in the real CLI across tool rounds, an event-triggered run and a later prompt, and asserts each request's messages start with the previous request's messages byte for byte, with identical tools. Collapse on return (Phase 3) was checked: it edits only the output of the cell that returned the tasks, once, at the first boundary after the model answered it, so the rewritten message is always among the previous request's last three messages and everything before it stays a cached prefix; the same test file asserts this. No change was needed. The trade-off that remains: that one rewrite re-sends at most the last few messages uncached once per collapsed cell (they shrink, so the request is smaller), while model-chosen `ctx.forget`/`ctx.summarize` of older items, compaction, and a change of tool descriptions (activating a code skill edits the `rlm` tool text) invalidate the prefix from the edited point by design.
- Live smoke (glm-5.3-flash through cliproxyapi, `-p`, a project whose test script sleeps 20 s then passes; asked to run the tests and meanwhile switch `greet()` to an f-string): the model started `./run_tests.sh` with `bash(..., yield_after=0)`, made the edit while the job ran, then waited on it with `await job.result()` rather than ending its turn, so no completion event was needed; 7 model calls, 59 s wall, both parts correct. Re-invocation by an event is covered by the scripted real-CLI tests (RPC and `-p`).
- Live smoke after auto-detach and hints (same model and `-p`, the test script now sleeping 45 s; two runs, 9 model calls in all): in both runs the model read `run_tests.sh`, saw the sleep, and chose `bash('./run_tests.sh', yield_after=0)` itself, made the f-string edit (it used the new `read` skill unprompted), then waited on `await job.result()` in the same turn (about 36 s and 35 s) rather than ending it, so the command never reached the 30 s auto-detach and no completion event was needed. No hint fired: the waits stayed under the 60 s `blocked-on-job` threshold. 4 calls / 69 s and 5 calls / 70 s wall, both parts correct each time. Auto-detach with the hint and re-invocation by the event are covered by the scripted real-CLI test.
- Cells do not yield (option C). A cell that returns "in progress" while it keeps running would need somewhere for the model's next cell to run. A second "side" kernel shares no variables with the busy one, so the model would be working in two namespaces with different contents, and anything it defined in the side kernel would be gone later; queueing the next cell behind the busy one reintroduces the stall. Long work in a cell is in practice a shell command, a subagent, a frame or a background agent, and all of those are now host-owned and non-blocking with completion events; pure-Python long computation can be written to a file and run as a job (`bash('python3 job.py', yield_after=0)`). So the kernel stays one cell at a time, and the non-blocking unit is the job or task, not the cell.

## Situational hints

- `src/ultron/rlm/hints.ts` (nano-rlm's supervisor hints): the rlm tool observes each lane's host requests and cell outcome and appends at most one line, `[hint:<tag>] … (Mute this hint: `await hints.mute("<tag>")`.)`, to the cell's result (after truncation; on a failed cell, to the error text). The result is an appended tool result, so hints never change earlier messages. Tags, in order: `stuck-loop` (loop-detector.ts: three failed cells in a row, a failed cell being one that raised or whose last `bash` exited non-zero other than a query command's exit 1; an A, B, A, B run of cells that differ only in whitespace and numbers with at least half of them failed; or eight failures in the lane's run; it asks for three hypotheses and a test of the likeliest, fires once per phase and escalates once at twice the threshold, a phase ending with a successful cell that is not a repeat and the detector resetting when the lane's run ends; while it handles a phase, `repeated-failure` stays quiet), `job-detached` (a plain `bash` came back running), `blocked-on-job` (the cell spent 60 s or more, overlapping waits counted once, in `job.result()` or `background.result` while completion events are on; waiting for subagents in `rlm.collect` or `agents.result` is the guide's advice once the root has nothing of its own left, so it earns no hint), `poll-loop` (the same status call, `shell.get`/`shell.result` of running work, `rlm.jobs`, `agents.status`/`tasks`/`inspect`, `background.list`/`inspect`, `rlm.list_subagents`, three times in a cell or in two consecutive cells, or `time.sleep`/`asyncio.sleep` in a loop around a status check), `repeated-failure` (the same exception type three cells in a row), `large-read` (the output was cut or a by-reference string over the handle threshold was shown, and the cell read a file), `output-truncated` (the output was cut in the middle). A muted or spent tag gives way to the next one.
- Secrets in cell output (`src/ultron/rlm/output-secrets.ts`): the text of each cell's result or error (stdout, stderr, the last value, a traceback) and runtime event summaries are masked before the model sees them: a credential becomes `[REDACTED:<kind>]`, the rest is unchanged, and values in the kernel keep their real content. `edit(old_str=...)` whose `old_str` holds a marker the file lacks fails with an explanation and writes nothing. `ULTRON_MASK_SECRETS=off` disables masking. The rules are `src/ultron/rlm/secret-patterns.json`, read by `src/ultron/secrets.ts`, the runtime's `secret_patterns.py` (a test keeps the two engines identical), the code-skill secret gate and `scripts/secret-scan.mjs` (`npm run scan:secrets`, CI, `pack-release.mjs`); each rule carries should-flag and should-not-flag canary examples that a test runs.
- `await hints.mute(*tags)`, `await hints.unmute(*tags)`, `await hints.muted()` (Python `hints_api.py`) are per lane; unknown tags are refused. Each tag fires at most 3 times per lane in a session (`ULTRON_HINTS_MAX`). Mutes and counts are the versioned session value `ultron.module/hints`. `ULTRON_HINTS=off` disables hints.

## File hooks and Loki guardrails

- Generic file hooks (`src/ultron/file-hooks.ts`): the kernel's `edit()` and a new `write(path, text)` skill send `{path, content}` to the host (`files.before_write`, only when the worker enables hooks with `ULTRON_FILE_HOOKS=1`) before touching the file. Every enabled guard sees each write, writes and guards in parallel (`asyncio.gather(edit(...), write(...))` checks together); a block raises `ValueError: <path> was not written: [<guard>] <reason>` and nothing is written. A guard that does not answer within its limit (5 s default) or fails lets the write proceed with a printed `[<guard>] <guard> did not check this write to <path> (...)` note: fail-open, never silent. After each cell (only while some guard watches cells), a metadata snapshot (`workspace-snapshot.ts`) is diffed with the previous one in the background; added and modified files whose content is not what a before-write check approved go to guards' `afterCellChanges` as `files`, approved ones as `checked`, removals as `deleted`. Findings are appended to the lane's next cell result. Per-guard checks, blocks, unchecked writes and time (this root turn, in all) are in the `rlm.pool` inspection (`guards`) and the RLM pane's kernel strip (`loki 85ms turn/1.4s 1 blocked`).
- Pi extensions reach the same hooks through two new events, `before_file_write` (`{path, content, cwd, lane}` → `{block, reason}` or `{message}`) and `after_cell_changes` (`{files, checked, deleted, complete, cwd, lane}` → `{message}`), bridged by `LegacyExtensionAdapter.fileGuards()`; each is active only while an extension handles it.
- Loki (`src/ultron/loki.ts`, the only Loki-specific module): the engine is bundled in `src/ultron/loki-engine/` (loki.py, the default policy template, LICENSE, `VERSION.json` with each file's sha256; `npm run loki:update -- <checkout|version>`, verified by `scripts/loki-update.test.mjs`). At worker start, in parallel with resource loading: python3 >= 3.11 is found (`ULTRON_LOKI_PYTHON`), and in a Git repository without `.loki/` that is eligible (auto-install on, no `CI`, root not `$HOME` or `/`, not under node_modules, not in `loki.ignoreRepos`, writable) `loki init --minimal` creates only `.loki/loki.py` and `.loki/loki.json`. Unless auto-commit is off, `CI` is set, a merge/rebase/cherry-pick/revert/bisect is in progress, HEAD is detached or `.loki` is ignored, `git add .loki` and `git commit -m "Add Loki guardrails" -- .loki` commit only that directory with the user's identity (no terminal prompts, bounded in time, the process group stopped with SIGTERM so git drops its index lock; never `--no-verify`); a refused commit unstages `.loki/` again. The one-time transcript note (`loki` custom message) opens the next root turn: "Loki set up and committed (<sha>)" or why not. The repository's own `.loki/loki.py` is used when present (older engines fall back to `--preview pi`, the same write envelope); otherwise the bundled engine with the default policy. `protect --file <rel> --preview ultron` runs before each write inside the repository (writes outside it are not checked); `hook --file ... --format json` runs after cells on changed files (up to 40) and the model is told three kinds of thing, never mixed (`LokiGuard.afterCellChanges`): new blocking findings ("N new findings from this cell's changes; fix these:"), advisory findings ("FYI (advisory, not blocking; no change required):", for example a function grown past the complexity threshold), and `NOT CHECKED` notes as one line, once per session ("not checked in this session (said once): ..."). A finding already shown and still present after a later cell shrinks to "N findings reported earlier are still open in <files>"; one that was fixed and comes back is new again. The guard record's outcome is `findings`, `advisory` or `clean` (a note alone is `clean`), and only `findings` and failed checks count as after-cell findings in the session report. The engine reports only what the edit introduced against the committed file (Python import and AST checks included, since the engine pinned in `VERSION.json`), so existing code in an edited file is not reported. An older repository engine without `--format json` (it does not name `json` in `context --host ultron`) has its text sorted into the same tiers (`classifyLokiText`). The project's interpreter is passed to the engine as `LOKI_PYTHON` for its import check (`findProjectPython`: `ULTRON_LOKI_PROJECT_PYTHON`, else the `python`/`python3` on `PATH` when it belongs to a virtual or conda environment, else `.venv`/`venv` in the session directory; never `ULTRON_LOKI_PYTHON`, which only runs the engine); with none, the engine looks in the repository root and otherwise reports new imports as not checked. While `.loki/` has uncommitted changes, Loki's post-write checks stop at "protected content changed", which is reported once as paused. Outside Git only before-write checks run (post-write checks need a base revision) and the session is told. `context --host ultron` (about 470 characters) is its own `<loki>` system-prompt section, not part of the runtime guide. `ULTRON_LOKI=off|advise`, `ULTRON_LOKI_AUTOINIT=off`, `ULTRON_LOKI_AUTOCOMMIT=off`, `ULTRON_LOKI_TIMEOUT_MS` and the global `loki` setting (`ultron setup` step 5) control it; `ULTRON_LOKI_BUILTIN=1` tells Loki's Pi extension (which also handles the two events) to stand down; `ULTRON_LOKI_LOG=<file>` appends every check as JSON lines.

## Session report (`/usage`, `ultron usage`)

- `src/ultron/session-report.ts` builds one report of what a session did, as JSON with the schema `ultron.session-report/1`: turns and wall time, root models, cells (count, failed, the REPL APIs their code names), depth (frames by model and outcome, sub-agents by model with nesting, verdict checks, worktree branches and merge outcomes, workflow runs, typed-agent tasks, background jobs) with a one-line verdict (`root only`, `depth 1: 99 frames, 0 sub-agents`, `depth 2: 6 sub-agents (2 nested)`), tokens and cost per lane kind (root, frames, sub-agents, other) and per model, guardrails (file-write guards such as Loki: checks, blocks, time; masked secrets; hints fired; steers; refused work), and memory (Jev decisions, memory operations). `src/ultron/session-report-text.ts` prints it, and the one-line-per-session table.
- Sources, all in the session file: the task journal `ultron.tasks/root` (sub-agents, frames, typed agents, background jobs, their parents, verdicts, checks and worktrees), the frame traces `ultron.rlm.frames/frame-*` (status, model, caller, budget spend), each lane's model (`pi.lane.config/<lane>`), each lane's runs (`pi.op.meta` names the lane, `pi.result` the outcome and times; a root turn is a run of `main`), the entries (a response's provider, model and reported usage; `rlm` tool calls and their results), the usage ledger `ultron.usage/root` (for a sub-agent that ran as a process of its own), `ultron.module/hints`, `ultron.jev.decisions/root`, `ultron.memory.state/root`, and the runtime counters below. An entry belongs to the lane whose branch tree it is in (lanes never share a tree), so usage is attributed per lane without the in-memory graph view (`agents.status {graph: true}`), whose model, token and timing fields do not survive the worker.
- `src/ultron/session-log.ts` reads the file without opening the session: line by line, keeping a digest (never an entry's text), skipping streamed-frame lists and a torn last line. It never writes (opening a session repairs a torn line by rewriting the file), so it is safe on a session a worker is running.
- Runtime counters (`src/ultron/session-stats.ts`, session value `ultron.module/stats`, versioned): what the runtime sees and nothing else kept. The rlm tool counts every cell where it runs (per lane kind: root, sub-agents, other; failed; the APIs its code names; secrets masked) and every host request by type; file hooks report each guard outcome; the nudgers and the budget hooks report steers and refused work (`NativeUsageLedger`'s `onRefused`, the `before_tool` and `before_request` blocks, an external root's refused cell); the host reports `rlm.merge` outcomes and each sub-agent's model; an external root's turns are counted with their time. The document holds counts, API names, task ids and times only. It is saved 500 ms after a change and when the worker closes, never per event; a failed write leaves the counters in memory and never fails a cell; a document in a newer format is left alone. A root run marks the counters used, so a session in which the root ran always has them.
- What each mode records. `ultron` and `ultron --claude`: everything (the root lane's entries are in the session; under `--claude` its responses come from the `claude-code` provider and their cost is the CLI's notional figure). `ultron claude`: the task journal, frame traces, ledger, hints, Jev decisions and the counters; the root's transcript, model, tokens and cost are Claude Code's and are reported as not recorded, and its turns and cells come from the counters. A sub-agent that ran as a Claude Code process has its usage in the ledger and its model in the counters; its own cells are in its own session. A session written before the counters existed reports those values as `null` with the reason in `unrecorded` (the report says `not recorded`); for sessions with a transcript, cells, masked secrets and steers are read from the entries instead, so they are complete for old sessions too.
- Cost: a response billed per token adds to `reportedUsd`; a response of a subscription provider (`claude-code`, or a provider the worker knows is on a subscription login) adds to `subscriptionUsd`; a response that used tokens and reported no price counts in `unpricedResponses` and prints as `unknown`. A sub-agent that reported no usage counts in `unmeasured` (`+?`). None of these is ever shown as zero.
- Surfaces: `/usage` in the native TUI (the worker answers the read-only inspection request `usage.report` from its session file plus the counters still in memory; also available over RPC `inspect` and the `ultron mcp` control socket); `ultron usage [session-id|path] [--last N] [--here] [--all] [--json] [--utc] [--sessions-root <dir>]` (`src/ultron/usage-cli.ts`), which needs no server and no model. With no argument it reports the most recent session of the current directory in which something ran; an id may be a prefix, or Claude Code's session id.
- Tests: `test/ultron-session-report.test.ts` (fixture sessions in each mode's shape: root only, frames only, nested sub-agents with verdicts and worktrees, `--claude`, `ultron claude` with and without counters; the printed report and table), `test/ultron-usage-cli.test.ts` (session lookup, `--last`, the JSON field sets, errors, and that nothing under the profile is written), `test/ultron-session-stats.test.ts` (the counters), `test/ultron-usage-report-cli.test.ts` (the real CLI with a scripted provider: frames, a nested sub-agent, a worktree child and its merge; the worker's report equals the file's), and one test each in `test/ultron-claude-root.test.ts` and `test/ultron-claude-mcp.test.ts` for the two Claude modes end to end.
- Limits: the frame trace index keeps 200 frames but every trace is kept, so frame counts are exact; Jev's log keeps its newest 200 decisions (the report says when it is full); a forked session's file holds the copied entries, so their usage is counted in the fork too; `scripts/eval-quality.mjs` still computes `childrenSpawned`, `childDepth` and `framesSpawned` from `agents.status` (its recorded result shapes are unchanged; `depth.subagents.count` and `maxDepth` use the same definition of nesting).

## Claude Code as the root agent (`ultron claude`, `ultron mcp`)

- `src/ultron/claude/`: `ultron mcp` (mcp-server.ts, over a minimal stdio JSON-RPC MCP server in mcp-protocol.ts: `initialize`, `tools/list`, `tools/call`, `prompts/*`, `resources/*`, `ping`, `notifications/cancelled`), `ultron claude` (launcher.ts), `ultron hook` (hooks.ts), `ultron watch` (watch.ts), `ultron guide` (guide.ts), and the recursive child runner (child.ts). main.ts loads the module only for these commands.
- One server process is one Claude Code session. It runs Ultron's runtime through `createUltronRuntime` (session-worker.ts, the same function the session worker uses) with `externalRoot` options: the root lane never runs; `ExternalRootController` (external-root.ts) runs each `rlm` call through the rlm tool's own execute on the root lane (truncation, hints, secret masking, Loki findings, `view_image` images as MCP image content), opens a root turn per Claude Code user turn (UserPromptSubmit hook, else the first cell) and closes it on Stop, checks the turn budget before each cell, and appends the research-loop brake and the wait nudge to the next result instead of steering. The Ultron session is created in the usual session dir and remembered per `CLAUDE_CODE_SESSION_ID` (`<agent dir>/claude-code/sessions/`), so a resumed Claude Code session reopens it; it is locked like a worker's.
- Events: `AsyncEventDispatcher` takes a `rootSink`; root-lane events go to the controller's inbox (at most 64, older ones counted as dropped) and lead the next cell result, or go out as UserPromptSubmit `additionalContext`. Child lanes are delivered as before. The guide (`rlmRuntimePrompt(..., {delivery: "next-call", externalRoot: true})`), the root lane's hints (`CellHints` `rootDelivery: "next-call"`: no `blocked-on-job`, job/poll wording points at the next result) and the wait nudge never say an event will wake the model; `ctx` is left out of the guide.
- Hooks (`ultron hook session-start|user-prompt|stop`, written by `ultron claude` into a temporary `--settings` file): the command forwards its stdin JSON to the server's control socket and prints the answer; any failure prints nothing and exits 0. SessionStart returns Loki's policy note and its one-time setup note; UserPromptSubmit returns recalled memory (`AutoMemory.beforeRun`: Jev gate, Hindsight, legacy bank) and waiting events; Stop passes `last_assistant_message` to retention (`AutoMemory.runEnded`) and ends the root turn (budget window, stuck-loop count, nudgers). Verified against claude 2.1.284 with `--include-hook-events`: all three fire, UserPromptSubmit `hookSpecificOutput.additionalContext` reaches the model, Stop input carries `last_assistant_message`, and `--settings` hooks run with `--setting-sources ""`. No blocking hook is used.

## Claude Code under Ultron's UI (`ultron --claude`)

- `--claude` (args.ts), `ULTRON_ROOT=claude` or the global `claudeCode.root` setting: main.ts calls `prepareClaudeRoot` (ultron/claude/worker-root.ts), which picks the root model (`claude-code/<id>` from `--model`, `ULTRON_CLAUDE_MODEL`, else `claude-code/claude-opus-5-5`; any other provider is refused), sets `ULTRON_ROOT=claude` and `ULTRON_SELF_COMMAND` for the worker. The worker moves the main lane to that model when a resumed session was on another provider.
- The claude-code provider takes a tool runner (`setClaudeCodeToolRunner`, a process-wide slot): a request that declares tools goes to it instead of failing. Every session worker (not `ultron mcp`) installs one (`installClaudeCodeLanes`), so any lane on a `claude-code/...` model with tools runs through Claude Code: the root under `--claude`, subagents that inherit its model, deep frames. Tool-free requests (frames, judges, `/review`) stay on the isolated one-shot path.
- `ClaudeRootRunner` (root-runner.ts): one `claude -p` process per lane run (key: the harness's `sessionId:lane`), started with `--print --output-format=stream-json --input-format=stream-json --verbose --include-partial-messages --tools= --strict-mcp-config --mcp-config=<bridge> --allowedTools=mcp__ultron__<tool>,... --setting-sources= --permission-prompts=none --disable-slash-commands --settings=<allow list> --model=<id> --system-prompt-file=<lane system prompt + Claude Code note> [--effort=<thinking level>] --session-id=<uuid>|--resume=<uuid>`, in the lane's cwd, with the parent Claude Code session variables removed and `MCP_TOOL_TIMEOUT` of 2 h. Each API message of the stream becomes one lane response: text and thinking deltas stream, `mcp__ultron__*` tool uses become tool calls (arguments streamed from `input_json_delta`), per-message usage comes from `message_start`/`message_delta`, and the response ends at `message_stop` with stop reason `tool_use` (the process keeps waiting on MCP) or at `result` (the CLI's `total_cost_usd`, as the difference from the process's previous `result`). The harness runs the tool calls; the next request of the run hands their results to the waiting MCP calls, by the tool-use id Claude Code puts in `_meta["claudecode/toolUseId"]`. Errors: `classifyFailure` (usage limit with window and reset, non-retryable; 429; 529; auth), a missing `--resume` session starts a fresh one. Abort kills the process group. The run's end (`run_end`) closes stdin (or kills the process when a call is open).
- Continuity: the lane's record (session value `ultron.claude-code.lanes`/`<lane>`: Claude Code session id, last settled response id, user messages already delivered after it) says where the transcript continues the session. A request whose transcript still ends in that response resumes and sends only what is new (tool results of an interrupted run as text, then the new user messages); a transcript that moved on (another model answered after `/model`, tree navigation) starts a new Claude Code session with the conversation rendered as `<conversation_so_far>`. Aborted and failed responses are not part of the replayed transcript; their input counts as delivered.
- Steering and follow-ups: user messages in a request of a running process go to its stdin before the tool results are released, so Claude Code has them queued (`queued_command`) when the results arrive and gives them to the model in the same turn; after a finished turn they start a new turn in the same process. Verified with claude 2.1.284 (Haiku): a message typed while an 8-second cell ran was answered in the same reply.
- Bridge (tool-bridge.ts): the worker listens on an owner-only socket in the control directory; `ultron mcp --bridge <socket> --token <token>` serves the lane's tools (names, descriptions and JSON schemas from the request) and forwards `tools/call` with the tool-use id. `mcp-protocol.ts` passes `_meta` to `callTool`.
- Worker hooks (worker-root.ts): `before_compaction` declines on claude-code lanes (Claude Code compacts its own context). Everything else is the native root lane: Jev/Hindsight, Loki notices, the async-event wake-ups, budgets, nudges and hints.
- TUI: the footer names the model `<id> (Claude Code)` without the provider prefix, marks costs `(sub)`, hides `(auto)` compaction, and shows the subscription windows from the last response's `claude_code_usage` diagnostic (the CLI's `rate_limit_event`).
- Live smoke (claude 2.1.284, tmux 160x45, isolated agent dir, Hindsight off, Loki on): Haiku computed with one cell and ran one `rlm.spawn` subagent (its own Claude Code session, shown in the auto-opened RLM pane as `claude-code/haiku`); a steered message was answered in the same turn; `ultron --claude --model claude-code/haiku -c` resumed the Claude Code session (no new session file) and recalled both results; one default turn ran on claude-opus-5-5.

## Controls

All optional controls (permission prompts, risk blocking, capability enforcement, completion gates, refinement approval, mandatory sandbox, cost cap, per-root turn and token limits) are off by default, reported by `agents.status`, and never prompt.

## Known limits

- `ultron --claude`: Claude Code streams no thinking text, so none is shown. The cost of a turn is known only at its `result`, so a turn's intermediate responses are charged tokens but no cost until the last one (a cost cap can be overrun by one turn). The context window shown is the catalog's (200k); Claude Code's own compaction decides when it compacts. A worker that is still running from an earlier non-`--claude` start of the same session keeps its settings until it exits. Claude Code keeps its session transcripts in its own config directory, as it does for any `claude --resume`.

- Claude Code as the root: nothing wakes the root between turns, so work that ends after the last reply waits for the next message; without Ultron's hooks (`claude mcp add ultron -- ultron mcp`) a root turn opens with the first cell and never closes, so per-turn budgets span the session and memory is not automatic. Claude Code subagents cannot be steered (`api.steer`) and do not take Ultron-model ids; their own frames and subagents are charged to their own server's ledger, not the parent's. Claude Code's MCP output limit (`MAX_MCP_OUTPUT_TOKENS`, 25k tokens by default) sits above Ultron's ~20 KB cell truncation.
- Inference frames: a retry or tool round (depth > 1) that the budget cannot cover is refused before it is sent (a `before_request` block, sized from the frame's previous request), and the frame reports `Incomplete`. If a request's payload outgrows that estimate, the lane is aborted and the request may still go out capped at one output token; its usage is charged, so the pool can be exceeded by that request's input. Token holds use an estimate (characters / 3 for the frame's own prompt, request bytes / 4 for follow-ups) and settle to the provider's count, so a provider that counts more tokens than the estimate can overrun the pool by the difference. The `rlm` cell a deep frame gets is a normal kernel (there is no sandbox), not a read-only one. Handles are not saved in kernel snapshots; reopen them with `rlm.open(digest)`. Frame lanes are session lanes, so the materialized views are stored in the session file.
- There is no sandbox. The tree memory cap is a resource limit, not isolation. The watchdog fallback can still overshoot by whatever the tree allocates within one poll (at most 100 ms once it is above 70% of the cap, 500 ms from below 40%; a single process can never exceed the per-process RLIMIT_DATA, so a jump from under 40% is bounded by that limit times the number of processes allocating at once), plus the time to scan /proc. Without `smaps_rollup` Pss fields (Linux < 5.9, or an unreadable file) it falls back to per-process RSS and over-counts copy-on-write sharing again. Only descendants are adopted: a process that escapes while the kernel itself exits on its own (a crash, or cell code calling `os._exit`) is killed only if an earlier watchdog scan saw it or it is still in the cgroup scope, and a process started outside the kernel (for example through `systemd-run` or an already-running daemon such as an IDE server) is never counted. Adopted orphans that exit stay zombies (no memory) until the kernel is replaced, because the kernel cannot tell them from its own unwaited children. The cgroup scope moves the kernel out of the worker's own cgroup, so a limit set on the worker's unit does not cover kernels.
- Without a sandbox, a model can read anything the user can, including test files outside the project. The live A46 run observed the model reading its own demonstration test; hostile-code or blind evaluation needs real isolation.
- The snapshot key cannot be hidden from model code, which runs as the same user: with the keyring it is no longer a file in the profile directory, but code can still ask the unlocked keyring for it (`secret-tool lookup application ultron purpose rlm-snapshot-key …`); with the file fallback it can read the file. In memory it is safe from the kernel only where ptrace is restricted (Yama `ptrace_scope` >= 1: a child cannot read its parent). Signing stops tampering by anyone without the key. When the keyring once held the key but is unreachable (for example over SSH), the worker uses a key for that process only rather than a second file key, so its snapshots do not outlive it; a locked keyring counts as unreachable after 5 s.
- Agent classes: model-driven methods run in a fresh child lane with no access to the calling object, so they see fields only as data and cannot call the object's other methods or change its fields (NOOA's CodeAct methods can); docstrings are not templated (`{self.x}`), because a descriptor must stay the same across calls to keep one generation. A class that is not at the top level of a cell, or that uses a name defined in another cell that is not restorable, is still usable but is not defined again after a restore (`agent.classes()` reports why).
- Native context edits (`ctx.forget`, `ctx.summarize`, collapse) are exported to Pi as plain `custom` entries, which Pi does not apply: a Pi resume of an exported session shows the full transcript to the model again. Edits cannot target an entry that lies before the newest compaction (it is only in the compaction's retained copy), so `ctx` refuses those ids. Collapse attribution is in memory: a worker restart between a cell and the model's next answer leaves that output uncollapsed (nothing is lost). A task that ends between cells is attributed to the next root cell, which may not be the one that printed it.
- Asynchronous execution: jobs are processes of the session worker and do not survive it (a worker restart marks them `interrupted`); a batch that mixes completions from different roots is charged to the newest one; events for a child lane that has finished wait as `nextRun` input and are seen only if the lane runs again (a retained instance). A client that sends a prompt at the moment an event starts a run gets Pi's "lane busy" answer and steers instead. The runtime guide names the default 30 s auto-detach wait; a different `ULTRON_BASH_YIELD_AFTER` is not reflected in it (the note on a detached result gives the actual wait). Hints are heuristics over host requests and cell text: `large-read` needs a file read in the cell's code, and a status call is only seen when it goes through the host.
- Pi import: branch-local context edits are applied by copying the path from the target to the last fork (copies are native-only and dropped on export), which matches Pi at every leaf; as for any baked edit, entries between a target and its edit show the edit natively. Edits Pi applies to a summary entry, or whose target is not on the edit's own path, are kept as entries but not applied (`unappliedContextEdits`). A folded root's calls lose per-task attribution; reconciliation accounts its journal tasks by the history's admission counts.
