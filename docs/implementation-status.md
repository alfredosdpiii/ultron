# Ultron implementation status

Ultron is a fork of Pi whose only agent runtime is the native RLM session worker. This file describes what is built. Whether each A01-A46 row is proven is decided by the acceptance runner, not by this file: see [a01-a46-acceptance.md](a01-a46-acceptance.md).

## Runtime

- Every agent run goes through the native session worker: the TUI, `-p`/`--mode json`, and `--mode rpc`. `--help`, `--list-models`, and `--export` never run the agent and use Pi's handlers. `--export` renders native session files.
- `--mode rpc` speaks Pi's JSONL protocol (`src/experimental/rpc-native.ts`); Pi's `RpcClient` drives it in tests. The event stream carries Pi's tool lifecycle (`tool_execution_start`, `tool_execution_update`, `tool_execution_end`). Models are full Pi `Model` objects; `get_tree`, `get_entries`, and `get_fork_messages` cover every branch in Pi's entry format (read from the worker's session storage); `get_messages`, `get_session_stats`, and `compact` return Pi's shapes. Extensions in the session worker reach the attached client through `extension_ui_request` lines (select, confirm, input, editor, notify, setStatus, setWidget, setTitle, set_editor_text) and wait for `extension_ui_response` with Pi's timeout and signal handling; with no client serving (`-p`), dialogs get Pi's defaults at once. `ctx.mode` and `ctx.hasUI` follow the client as in Pi: the CLI tells each Session worker it starts which client it is for ("tui", "rpc", "print", "json"); for the TUI and RPC, `hasUI` is true from `session_start` on and UI calls made before the client attaches are queued for it (Pi's defaults if it has not polled within 30 s); in `-p`/`--mode json` runs it is false. The TUI answers select and confirm with its selector and input and editor with Pi's extension input and editor components. `fork` and `clone` (RPC, and the TUI's `/fork` and `/clone`) create a new session holding only the main lane's path from the root to the entry (fork: any user message in the tree; clone: the current position), with the labels of the copied entries, as in Pi; `--fork` (TUI, RPC, and `-p`) copies the whole session, as Pi's does. Before a fork or clone, the source Session's extensions get Pi's `session_before_fork` (`entryId`, `position`) and can cancel it; the fork's extensions start with `session_start` reason "fork" and the source file, and the source worker's extensions see `session_shutdown` reason "fork" with the fork's file when it retires (unless the Session is used again first). The TUI has Pi's `/tree` over the native tree (branch summary prompt, labels, filters), and a double Esc on an empty idle editor opens the tree or the fork selector per Pi's `doubleEscapeAction` setting. Remaining difference: a worker keeps the mode of the client it was started for, so a later client of another kind attaching to a still-running worker sees that mode (and `hasUI` follows whether a client serves the UI). The Ultron-specific `inspect` command exposes the read-only inspector.
- `-e/--extension <path>` loads extension files in the session worker in addition to discovered ones, and `--no-extensions` skips discovery, as in Pi (paths resolve against the client's cwd).
- Pi extensions from the profile run inside the session worker through the legacy adapter. To stop one loading without deleting it, add an exclusion to the `extensions` setting, for example `"extensions": ["-extensions/jev/index.ts"]` in `<agentDir>/settings.json`. The setting takes exact `-path`, glob `!pattern`, and `+path` forms, with paths relative to the agent directory. This is how to retire the Pi Jev extension. Ultron now does its automatic memory natively. Its model pin and tool guard are deliberately not ported.
- Extension slash commands are registered directly (`/name`, as in Pi) and via `/extension <name>`. `/agents`, `/memory`, `/skills`, `/experiments`, `/goals`, and `/progress` read recorded runtime state without starting work or searching.
- Busy session workers survive the client exiting: background jobs, child lanes, and a root turn in flight keep running, the next `ultron` reattaches, and idle workers retire. Leaving the app (Ctrl-C twice within 500 ms or Ctrl-D on an empty editor in the TUI, a signal to the TUI or RPC process, closing RPC stdin) is not an abort; Esc in the TUI (which, as in Pi, first returns queued messages to the editor) and RPC `abort` are. A single Ctrl-C clears the editor. In `-p`/`--mode json` print runs, SIGINT, SIGTERM, and SIGHUP abort the running turn before the process exits, as in Pi. After a hard kill, idle workers exit within about a second and busy ones finish first.
- `ultron migrate import-pi | export-pi | backup | restore` moves whole Pi session trees in and out (every branch, labels, model and thinking-level history, context edits applied per branch, Pi-reported usage imported into the usage ledger as a marked historical root; Pi-only entry types kept as `pi-session:<type>` custom entries) and rehearses profile backup and restore.
- `/rlm` (Ctrl+R) shows a live RLM panel: the task tree with states and results, the root kernel's current cell, admitted tasks, wall time and cost, and the kernel pool. `/jev` (Alt+J) shows Jev's recent decisions (triage routes, recall gates, retention) from a bounded, hashed decision log, and whether Jev and Hindsight are available. Both collapse to a footer line.

## RLM host

- Each lane (the root and every task) has its own persistent Python kernel. Kernels receive no credential-like environment variables and no worker control channel (`ULTRON_RLM_ENV_ALLOW` passes named variables through). A pool caps live kernels (16), evicts idle ones after a snapshot, never evicts a running cell, and pins retained instances' lanes (up to half the pool). Kernels run under per-process memory limits (`ULTRON_RLM_MAX_MEMORY_MB`, default 4096), a whole-tree memory cap over the kernel and every process its cells start (`ULTRON_RLM_MAX_TREE_MEMORY_MB`, default twice the per-process limit, 0 disables), and a per-cell CPU budget (`ULTRON_RLM_MAX_CPU_SECONDS`, default 1800); exceeding any fails the cell clearly and the kernel is replaced if needed. The tree cap uses a transient systemd user scope (`systemd-run --user --scope -p MemoryMax=… -p MemorySwapMax=0 -p OOMPolicy=continue`) when a probe shows it works without root, else a host watchdog that sums the proportional memory (Pss_Anon+Pss_Shmem+SwapPss from `smaps_rollup`, so copy-on-write pages shared by forked children count once; RssAnon+RssShmem+VmSwap where PSS is unavailable) of the kernel's descendants from /proc every 500 ms, every 250 ms above 40% of the cap and every 100 ms above 70% (`ULTRON_RLM_TREE_MEMORY_BACKEND=auto|cgroup|watchdog|off`). The kernel runs in its own session and makes itself a child subreaper (`PR_SET_CHILD_SUBREAPER`) before any cell runs, so processes that double-fork out of a cell are reparented to the kernel and stay counted. On a limit hit or shutdown the host stops the kernel, SIGKILLs its descendant tree in repeated sweeps (catching orphans it adopts meanwhile), then its process group, the kernel, descendants seen by earlier watchdog scans, and any process left in the cgroup scope. Snapshots are HMAC-signed by the host with a per-profile key. Snapshots are signed with `<agentDir>/rlm-snapshot.key` by default; `ULTRON_RLM_SNAPSHOT_KEY_STORE=auto` (or `keyring`) opts into keeping the key in the OS keyring via `secret-tool` (an existing key file is moved there). The keyring hides the key only from casual reads of the profile, not from model code running as the same user, and a locked or unreachable keyring costs restorable snapshots, so it is off by default; unsigned or tampered snapshots are refused.
- The host knows which lane issued each request, so tasks record their parent, child lanes can only query their own subtree, and cancelling a task stops its whole subtree.
- Strategies: `deterministic`, `predict` (one tool-free model call with bounded repair), and `rlm` (a model lane). All share admission, idempotency, timeouts, usage accounting, and the durable journal. Results are always `verification: "unverified"`; only explicit checks (progress reassessment, goals, release gates) can say more.
- The usage ledger (`ultron.usage`) keeps the 50 most recently active roots (root turns and background jobs) call by call. Older roots with no open reservation whose wall deadline has passed are folded into a bounded per-session history (totals by kind, model spend, unknown-priced calls, task admissions by status), so the document stays bounded. `agents.status` shows the current root and a `session` total that includes the folded history; reconciliation compares each root with its own records and the session total with all records plus the history.
- `agents.spawn`, `rlm.spawn`, and module-started tasks outlive the Python cell that started them; `agents.invoke` waits inside the cell. Each root turn gets its own wall budget (`ULTRON_MAX_WALL_MS`, default 30 minutes) and admission cap (`ULTRON_MAX_ADMITTED_TASKS`, default 24); a child's deadline is capped at its root's remaining budget. An optional cost cap (`ULTRON_MAX_COST_USD`, unset by default) refuses new model-backed work once reached or when pricing is unknown. Optional per-root turn and token limits mirror nano-rlm's `max_total_turns` / `max_total_tokens` (settings `rootBudget: {maxTotalTurns, maxTotalTokens}`, overridden by `ULTRON_MAX_TOTAL_TURNS` / `ULTRON_MAX_TOTAL_TOKENS`; `off` removes a limit; unset by default). The usage ledger counts every model response of a root turn and of every task lane it admitted (and each `predict` attempt) with its provider-reported tokens; once a root reaches a limit, new model-backed work is refused and its lanes' tool calls are blocked with the limit error (`Usage turn limit reached for root turn:…: 40 of 40 model turns used (max_total_turns …)`), which ends the run. Each root turn starts fresh; `agents.status` shows `usage.turns`. Without a limit nothing is counted or written per response.
- Workflows validate before any effect and support fan-in, conditional routes, any-of joins (`join: "any"`), bounded revision loops (`revise: {from, until, max_rounds <= 10}`, each round its own task), explicit skips and failures, and keyed nodes and workflows.
- Host modules (`src/ultron/*.ts`, Python classes in `src/ultron/rlm/*_api.py`):
  - `schedules` / `goals`: slot-keyed schedules that never double-fire, missed ticks coalesce, goals achieved only by passing required checks.
  - `skills`: version-pinned (content hash), explainable selection; frontmatter cannot grant capabilities.
  - `agent_message`: parent/child messaging with verified senders, deduplication, expiry, inbox caps, optional steering, and verifier isolation.
  - `progress`: evidence receipts, progressing/busy/stalled/finished assessment, completion claims verified only by a passing verifier; budgets never extend.
  - `instances`: retain a completed task and continue it on its own lane with fresh scratch and a persistent `state` dict.
  - `grants`: scope/revision/policy/owner/expiry-bound approvals, rechecked on use; dormant by default.
  - `gates`: frozen release-gate definitions and baseline/candidate comparison where required regressions block.
- Refinements (versioned lessons) reach later task prompts, follow the conversation branch (a lesson from an abandoned branch never applies), refuse protected targets and capability requests, and are content-validated. Approval is off by default and recorded as `not_required`.
- Memory uses Hindsight at `http://localhost:8888` by default (bank `ultron`, created on first use; `ULTRON_HINDSIGHT_URL` overrides, `off` disables). Automatic memory is gated by Jev; deliberate `memory.prepare`/`memory.propose` calls from agent code skip the relevance gate, and writes Jev rates sensitive are still refused. Memory withholds forgotten and superseded items even when the backend still returns them, labels evidence classes, records scope denials, and reuses recorded decisions.
- Automatic per-turn memory (`src/ultron/auto-memory.ts`) runs on root-lane runs only, never on child task lanes, and needs both Hindsight and Jev. Before a run, the user's request goes through Jev's recall gate (the non-explicit path: a low score makes no Hindsight call). Recalled evidence is injected as an untrusted `ultron-memory` custom message. That message stays in the transcript, the TUI shows it muted, and `memory.why("auto:<runId>")` explains it. After a completed run, Jev's retention policy judges the request and the answer. Only a keep with confidence of at least 0.65 is stored, as `[User] … [Assistant] …`. Aborted or failed runs are never stored. Scope is `project` by default (`ULTRON_AUTO_MEMORY_SCOPE=session|project|global`). `ULTRON_AUTO_MEMORY=on|recall|off` (default `on`) controls it. Recall and retain decisions appear in `jev.decisions` and the `/jev` panel. A Jev or Hindsight failure is swallowed, so the turn runs without memory. Jev reads `TYPESAFE_API_KEY` or, like the Pi extension, `<agentDir>/jev-api-key`. When the gate retrieves, the Pi Jev extension's Hindsight bank (`ULTRON_HINDSIGHT_LEGACY_BANK`, default `omp`; `off` disables) is also searched read-only, without tags. Up to 12 deduplicated results are appended under "Earlier memory (from Pi, read-only)". A missing bank counts as empty, and Ultron never writes to it.
- Ultron does not route or pin models from Jev triage. The model is the one from `--model`, `/model`, or settings. Triage is available to agent code as `jev.triage`.

- Versioned session values (unreal-agent invariant, `src/ultron/format-version.ts`): every document Ultron writes to the session carries a format version (`ultron.tasks`, `ultron.definitions`, `ultron.usage`, `ultron.memory.state`, `ultron.jev.decisions`, the `ultron.module/*` documents of family, progress, schedules, instances, grants, release-gates and skills, and the `ultron.local` refinements, experiments, artifacts and artifact references). Entries (tasks, calls, memory operations, refinement events, decisions) inherit their document's version, since each document is replaced whole. A document without a version is read as version 1. A newer version fails explicitly, naming the value and version (`Cannot resume: session value ultron.tasks/root has format version 2, but this Ultron reads only format version 1 …`), and is never rewritten: the session worker checks these values before loading any of them (artifacts, which can be large, when read), and each store checks again on load. Transient or foreign values are not versioned: `ultron.session.start/fork` (deleted on first read) and the `ultron.pi.*` import records (Pi's own entry format and a copied-entry id).
- A research-loop brake steers the root agent to answer after 10 consecutive tool-call rounds in one turn, and again more firmly at 20 (`ULTRON_TOOL_ROUNDS_NUDGE`, 0 disables). It never aborts; Esc does.

## Evals

- `scripts/eval-quality.mjs` compares stock Pi and Ultron on frozen task sets: `default` (the release-gate set), `hard`, and `judged` (`evals/quality/tasks-judged.mjs`: a refactor's quality, an explanation of a module, a design note). `--self-check` validates a set without model calls.
- LLM-judge tier (`scripts/eval-judge.mjs`): a task's `judge: {rubric, inputs, passAt, model?}` is scored after the run by a fixed judge (`--judge-model`, default `cliproxyapi/glm-5.3-flash`, run through stock Pi with no tools). Prompt, raw replies, per-criterion scores and reasons, and the normalized score are kept in `record.judge` and summarized per variant as `judged` next to the deterministic `passRate`. Judged tasks keep a deterministic sanity check (`verify`), which stays the pass/fail of record; a malformed judge reply is re-asked once, then recorded as an error. The judge never gates a release: `npm run gate` reads only the default set's deterministic pass rates. `--self-check` on the judged set checks each rubric's wiring against the reference solution with a fake judge; `--judge-live` also scores the references with the real judge.
- Uptake metrics in every record: `toolsByName`, `framesSpawned` (tasks with an `rlm-*` definition, from `inspect agents.status`; counted from the rlm tool's code when the host cannot be inspected; null for Pi) and `rootUnseenBytes` (reported only once the host exposes `uptake.rootUnseenBytes` or `uptake.handleBytesLoaded` / `uptake.handleBytesPrinted` in `agents.status`; null until then). Summaries aggregate them per variant (`uptake`: tool totals, share of runs using `rlm`, frame and unseen-byte totals and medians).

## Controls

All optional controls (permission prompts, risk blocking, capability enforcement, completion gates, refinement approval, mandatory sandbox, cost cap, per-root turn and token limits) are off by default, reported by `agents.status`, and never prompt.

## Known limits

- There is no sandbox. The tree memory cap is a resource limit, not isolation. The watchdog fallback can still overshoot by whatever the tree allocates within one poll (at most 100 ms once it is above 70% of the cap, 500 ms from below 40%; a single process can never exceed the per-process RLIMIT_DATA, so a jump from under 40% is bounded by that limit times the number of processes allocating at once), plus the time to scan /proc. Without `smaps_rollup` Pss fields (Linux < 5.9, or an unreadable file) it falls back to per-process RSS and over-counts copy-on-write sharing again. Only descendants are adopted: a process that escapes while the kernel itself exits on its own (a crash, or cell code calling `os._exit`) is killed only if an earlier watchdog scan saw it or it is still in the cgroup scope, and a process started outside the kernel (for example through `systemd-run` or an already-running daemon such as an IDE server) is never counted. Adopted orphans that exit stay zombies (no memory) until the kernel is replaced, because the kernel cannot tell them from its own unwaited children. The cgroup scope moves the kernel out of the worker's own cgroup, so a limit set on the worker's unit does not cover kernels.
- Without a sandbox, a model can read anything the user can, including test files outside the project. The live A46 run observed the model reading its own demonstration test; hostile-code or blind evaluation needs real isolation.
- The snapshot key cannot be hidden from model code, which runs as the same user: with the keyring it is no longer a file in the profile directory, but code can still ask the unlocked keyring for it (`secret-tool lookup application ultron purpose rlm-snapshot-key …`); with the file fallback it can read the file. In memory it is safe from the kernel only where ptrace is restricted (Yama `ptrace_scope` >= 1: a child cannot read its parent). Signing stops tampering by anyone without the key. When the keyring once held the key but is unreachable (for example over SSH), the worker uses a key for that process only rather than a second file key, so its snapshots do not outlive it; a locked keyring counts as unreachable after 5 s.
- Pi import: branch-local context edits are applied by copying the path from the target to the last fork (copies are native-only and dropped on export), which matches Pi at every leaf; as for any baked edit, entries between a target and its edit show the edit natively. Edits Pi applies to a summary entry, or whose target is not on the edit's own path, are kept as entries but not applied (`unappliedContextEdits`). A folded root's calls lose per-task attribution; reconciliation accounts its journal tasks by the history's admission counts.
